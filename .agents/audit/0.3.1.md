## 해결 방법

아래는 감사자의 보완 제안이다. PL·Advisor가 검토하거나 사용자가 수용한 것으로 기록하지 않는다. 설치된 역할 규칙상 감사 위반의 해결책 논의는 PM이 맡아 PL/discussion 및 개인 위임표의 Advisor 위원들에게 독립적으로 의견을 받고, 원문과 소수 의견을 보존해 사용자에게 보고해야 한다. 감사 역할은 다른 모델을 호출하지 않는다.

### 추가 비판과 해결 방법

**A1 — 중간: 추가 작업을 허락받은 것을 변경 spec 요약 승인으로 대신했다.**

`AGENTS.md`와 설치된 spec §2.3–4, implement §2.4는 작업 단위를 추가할 때 변경 spec의 요약을 보여 주고 응답받도록 한다. `eb56151`은 W-12·W-13을 추가했지만 summary를 그대로 두었고, 승인 rev `637e3ae`에는 이 두 단위가 없다. 사용자 “그렇게 해.”가 안정화 제안의 허락이라는 사실은 분명하므로 무승인 구현이라고 부르지는 않는다. 그러나 정해진 요약 절차를 지킨 것도 아니다.

PM은 S-29·S-30/W-12·W-13/V-14·V-15와 공통 문서 요구를 포함한 변경 요약을 작성하고 자체 검토 기록을 남긴 뒤 사용자 확인을 받아야 한다. 새 확인은 **머지 뒤 보완**이라고 기록하고 당시 승인으로 바꾸지 않는다.

**A2 — 중간: 감사 해결책 논의 생략의 예외를 정해진 위치에 기록하지 않았다.**

“해결책이 문제 없는 것 같으면 패스. 애매하면 받아.”는 조건부 허락이다. PM이 이를 사용했다고 감사 처리 절에 적었지만, `AGENTS.md`가 요구하는 intent의 일회성 `waivers:`에는 없다. 사용자 허락이 없었다는 비판이 아니라, 허락의 범위·조건·적용 사실을 정식 예외로 남기지 않았다는 비판이다.

PM은 해당 발언, 적용한 단계, 조건을 충족한다고 판단한 이유, `scope: once`와 사후 기록 사실을 추가해야 한다. 이 허락을 모든 후속 감사 해결책에 대한 상시 면제로 늘리지 않는다. 특히 A3의 증거 공백처럼 판단이 남은 문제까지 이미 면제됐다고 간주할 수 없다.

**A3 — 높음: 모델 검증 원본이 없는데 보완 완료로 보고했다.**

첫 감사는 실제 응답 모델을 식별할 원본 증거를 요구했다. 추가 로그에는 PM이 옮긴 필드 값만 있고, `R/notes-for-audit-2.md`는 원본 부재를 명시한다. 그런데 `eb56151`의 메시지와 `R/pr35-view-merged.json`의 본문은 지적 4를 `remedied`로 묶었다. 사용자 “나는 지금 잘 되는 것 같은데?”는 사용 경험에 대한 말이며, S-14/V-5의 증거 기준을 폐기하는 명시적 승인으로 확대할 수 없다.

PM은 “목록 유지에 대한 사용자 판단”과 “검증 증거 충족 여부”를 분리해 완료 주장을 정정해야 한다. 원본을 확보할 수 있으면 출처·시각·실제 응답 모델을 식별할 출력 경로를 제공한다. 새 실행은 사후 검증으로 표시한다. 확보하지 못하면 확인 불가를 유지하고, 기준 변경 또는 잔여 문제 수용을 사용자에게 명시적으로 받아 기록해야 한다. 과거 감사 원문과 master 이력은 고치지 않는다.

**A4 — 낮음: master SHA라고 선언한 완료 기록에 브랜치 SHA를 남겼다.**

`20f6b8f`의 W-12·W-13 참조는 각각 `a2603a2`, `b769d6f`다. 감사자는 두 목록과 tree를 대조해 실제 대응을 확인할 수 있었지만, spec 자체의 선언과 참조가 불일치한다.

후속 기록 커밋에서 `9244c15`, `7dbdde2`로 보정하고 PR #35 대응표를 영구 기록에 남긴다. 원래 승인·리뷰가 가리킨 브랜치 SHA는 지우지 말고 대응 관계로 보존한다.

**A5 — 낮음: 추가 단위에 적용되는 공통 문서 요구를 누락했다.**

spec S-21은 `harness/CHANGELOG.md`의 0.3.1 절에 단위마다 한 줄을 요구한다. 새 두 단위의 파일 목록에 그 파일을 적지 않았다는 사실만으로 S-21이 면제되지는 않는다. 범위 전체에서 changelog는 변경되지 않았다.

PM은 두 항목을 보완하거나, 이 두 안정화 단위에 공통 요구를 적용하지 않으려는 의도라면 spec 변경 요약에 예외를 명시해 확인받아야 한다. 이는 루트 제품 소스의 문서 요구이며 설치된 `.agents/harness/`를 손으로 고치라는 뜻이 아니다.

**A6 — 낮음: 범위 첫 기록 커밋의 메시지가 요구 형식을 충족하지 않는다.**

`d140db5`에는 bullet 본문이 없다. 첫 감사 전에 작성된 커밋이라는 경위를 함께 남기되, 이번 범위의 위반에서 제외할 근거는 없다.

이미 머지된 메시지를 다시 쓰지 않는다. 사용자 처리와 회고에 이 범위를 명시하고 후속 커밋에서 요구 형식을 유지한다.

추가 증거 요청은 PM에게 남긴다. 변경 spec 자체 검토, 보완분의 build와 V-14 지정 실행, 리뷰→검증 순서, 당시 분기·개별 gate 기록이 있으면 원본 경로를 제출해야 한다. 없으면 확인 불가로 확정한다. 뒤늦게 만든 증거를 당시 실행의 증거로 부르지 않는다.
