## 요구 해석
- S-1 TUI 라이브러리로 `@clack/prompts`를 런타임 의존성에 하나 더한다. 화면 코드는 `Prompter` 인터페이스(`select`, `multiselect`, `text`, `confirm`. 반환값은 값 또는 `BACK`·`EXIT`)로만 화면을 그린다. 실제 구현은 `clackPrompter`이고, 테스트는 답을 차례로 내주는 `scriptedPrompter`를 쓴다. 기존 `Asker`(stdin·defaults)도 그대로 둔다. ← 영향 범위 "TUI 라이브러리 의존성 추가", 제약 "런타임 의존성은 최소로", "Windows·macOS·Linux 터미널 모두에서 동작한다"
- S-2 새 명령 `reins config`(인자 없음)를 둔다. stdin과 stdout이 모두 TTY이면 설정 메인 화면을 띄운다. 항목은 `models and roles configuration`(첫 항목)과 `exit`이다. TTY가 아니면 화면 없이 `configure bindings --show`와 같은 해석 표를 출력하고, 바꾸는 명령(`configure bindings --set … [--local]`) 안내 한 줄을 붙인 뒤 exit 0으로 끝난다. `--json`이면 그 표를 JSON으로 낸다. `configure bindings|gates`와 그 플래그는 바뀌지 않는다. ← "`reins config` → 설정 메인 화면. 첫 항목 …", 제약 "터미널이 아니거나 … 비대화형으로 동작한다. 기존 플래그와 `configure` 명령은 그대로"
- S-3 models and roles 화면: 맨 위에 `< Configuration`(메인으로)과 `exit`가 있다. 그 아래 범위 전환 `scope: local | global`이 있다(local은 `.loctx/bindings.local.yaml`, global은 `.agents/harness/bindings.yaml`, 기본값 local). 이어서 역할 ON/OFF(multiselect. local 범위에서 팀 값과 다른 역할에는 `(local)` 표시. pm·implementer·verify-tool은 목록에 넣지 않고 "always on"으로 표시)가 오고, 역할마다 `[ON|OFF] <role>  <vendor> <model> (<source>)` 한 줄이 온다. 역할 줄을 고르면 역할 화면(S-5)으로 간다. 고른 값은 바로 그 범위의 파일에 쓰고 화면을 다시 그린다. global에 쓰면 생성물을 다시 만들고 "commit bindings.yaml" 안내를 낸다(지금 `configure bindings --set`과 같은 경로). ← "models and roles 화면: 범위 선택 local / global, 역할마다 ON/OFF, 역할을 고르면 다음 화면", "상단 `< Configuration` … `exit`로 종료"
- S-4 역할 OFF 저장(추가만): global은 `bindings.yaml`의 `roles.<r>.enabled: false`, local은 `bindings.local.yaml`의 `roles.<r>.enabled: false`다. local 스키마의 `roles.<r>`는 `model`과 `enabled` 중 하나 이상을 요구하도록 넓힌다. 실제로 켜져 있는지는 고정 역할이면 ON, 아니면 `local enabled ?? 팀 enabled ?? true`로 정한다(모델 덮어쓰기와 같이 local이 양쪽으로 이긴다). local `enabled: true`는 팀이 끈 역할을 그 사용자에게만 켜고, local `enabled: false`는 팀이 켠 역할을 끈다. 어느 층에서든 고정 역할에 적힌 `enabled: false`는 무시하고 status가 경고 한 줄을 낸다. TUI와 `configureBindings`는 고정 역할을 끄는 요청을 거절한다. 바인딩 항목은 꺼도 남는다(모델 선택 보존, T1 `bindings-valid`, `metrics record`). ← "역할마다 ON/OFF(pm·implementer·verify-tool은 ON 고정)", 영향 범위 "역할 on/off, 추가만"
- S-5 역할 화면: 벤더 목록에는 `vendors()`가 감지한 벤더만 나온다(claude는 항상 나옴). 벤더를 고르면 모델 목록을 보인다. google·cursor는 `listModels`(`ModelCache` 경유, 10초 제한)로 가져오고, 실패하면 이유 한 줄과 함께 알려진 목록을 보인다. claude·openai(그리고 목록을 가져오지 못한 벤더)는 알려진 목록을 보인다. 알려진 목록은 `harness/roles/*.md`의 `default_binding`·`fallback_binding`, `CONFIRMED_MODELS`, 현재 팀·local 바인딩 가운데 그 벤더(`vendorOf`)의 모델을 중복 없이 모은 것이다. 목록 끝에는 늘 `other (type a model ID)`가 있다. 모델을 고르면 S-3의 범위에 쓰고 models and roles 화면으로 돌아간다. `REINS_NO_VENDOR_SPAWN`이면 vendor CLI를 실행하지 않는다(기존 `newModelCache`·`spawnModels` 규칙). ← "역할 화면: 이 PC에 설치된 벤더 중 하나를 고르면 그 벤더의 모델 목록을 가져와 …", 제약 "모델 목록은 벤더 CLI가 제공할 때만 실제로 가져온다"
- S-6 꺼진 역할의 일은 누가 맡나: 역할 파일 frontmatter에 `covered_by: <role>`을 더한다(추가만). planner→pm, pl→pm, lookup→`caller`(부른 역할이 직접 찾음), code-review→pl, qa-design→pm, qa-run→verify-tool(실행)과 pl(판정), deploy→pm(사전 릴리스 루프와 A2 규칙은 그대로), docs→pm, advisor→user(사슬 끝)다. 맡은 역할은 자기 `must_not`에 꺼진 역할의 `must_not`까지 지킨다. 자기 작업을 판정하게 되면(예: pm이 쓴 spec의 pm 리뷰) 그 판정은 사슬의 다음(pl → pm → advisor → user)으로 넘긴다. `resolveBindings` 결과에 `enabled`와 `covered_by`를 더하고(JSON 키는 추가만), `reins status` 텍스트는 `off → <covered_by>`로 보인다. reins-loop SKILL.md에 "status의 `enabled: false` 역할은 부르지 말고 `covered_by`가 맡는다" 한 문단을 더한다. T1(ticket-start)은 ticket `role:`이 그 사용자 기준으로 꺼진 역할이면 WARN(`role <r> is off — covered by <c>`)만 내고 판정은 CONTINUE다. 막는 것은 0.2의 단계 깎기에서 한다. ← "역할을 끄면 그 역할의 일은 pm이나 상위 역할이 맡는다", 영향 범위 "역할·스킬 문서"
- S-7 생성물: `generateVendorFiles`는 지금처럼 커밋된 팀 파일만 읽는다. 팀이 끈 역할(고정 역할 제외)은 `.claude/agents/reins-<r>.md`를 만들지 않는다. 이전에 만들어진 파일은 `generated.yaml` 기준으로 `configure`·`update`가 지운다. local `enabled`는 어느 쪽이든 생성물을 바꾸지 않으므로 다른 사람에게 drift가 생기지 않는다. 팀이 끄고 local이 켠 역할은 agent 파일이 없으므로, 스킬이 `reins status --json`의 해석 모델로 그 역할을 부른다(Claude면 일반 subagent에 역할 파일 본문을 넘김). status는 그 역할을 `on (local)`으로 보인다. reins-loop에 "agent 파일이 없는 역할은 해석 모델로 부른다" 한 줄을 더한다. ← 영향 범위 "역할 ON/OFF 저장과 생성물"
- S-8 install의 네 질문(벤더·언어·게이트 확인·하위 게이트)을 타입이 있는 질문으로 묶는다. TTY이고 `--mode manual`이며 `--json`이 아니면 화면으로 묻는다. 벤더는 multiselect(감지된 벤더 미리 선택, claude 고정), 언어는 select(`ko`, `en`, other→text), 게이트는 목록을 보여 주는 confirm, 하위 게이트는 multiselect다. TTY가 아니면 `askerPrompter(asker)` 어댑터가 지금과 같은 질문 문자열과 파싱으로 stdin 줄을 읽는다. auto 모드는 `defaultsAsker` 그대로다. ← "install의 질문(벤더·언어·게이트·하위 게이트)", 제약 "터미널이 아니거나 … 지금처럼"
- S-9 update: TTY이고 `--yes`·`--dry-run`·`--json`이 없으면, 먼저 dry run으로 계획을 만들어 보여 준다(새로 만들 파일·바꿀 파일·지울 파일, bindings 이동, override 블록, changelog 항목). 그다음 confirm을 받고, yes일 때만 실제로 실행한다. no면 아무것도 쓰지 않고 exit 0이다. `--yes`(새 플래그)를 주거나 TTY가 아니면 지금처럼 바로 실행한다. ← "update의 변경 확인"
- S-10 설계서 양판 §5(bindings `enabled`, 고정 역할, local 우선, `covered_by`), §6(팀이 끈 역할은 생성 안 함, local로 켠 역할은 해석 모델로 실행), §9(`config` 명령, TUI, 비대화형 규칙, `update --yes`, install 질문 화면, `configure bindings --enable|--disable [--local]`)와 §2 역할 표 아래 한 줄(고정 역할·`covered_by`)을 코드보다 먼저, 같은 커밋에서 고친다. README 양판 Commands 표에 `config` 줄을 더하고 `configure bindings`(`--enable`·`--disable`), `install`·`update` 설명을 고친다. reins-setup SKILL.md는 "사용자가 터미널에서 `reins config`로 바꿀 수 있다"를 안내하고, 에이전트는 플래그 형식을 그대로 쓴다. ← 영향 범위 "설계서 양판 §5·§9, README 양판", AGENTS.md 불변식
- S-11 비대화형 역할 ON/OFF: `reins configure bindings --disable <role…> | --enable <role…> [--local]`. TTY가 없어도 동작하고 묻지 않는다. `setRoleEnabled`를 쓰고, global이면 생성물을 다시 만든다. 고정 역할(pm·implementer·verify-tool)을 `--disable`하거나 없는 역할을 주면 아무것도 쓰지 않고 exit 1이다. `--set`과 함께 쓸 수 있다. 에이전트와 CI는 이 형식을 쓴다(reins-setup도 이 형식). `--json`은 기존 `ConfigureResult`에 바뀐 역할을 담는다. ← 제약 "터미널이 아니거나(CI·파이프) 플래그를 주면 지금처럼 비대화형으로 동작한다", pm 결정(2026-10-28)
## 설계
- **라이브러리 비교.** ① `@clack/prompts`: 의존성은 `@clack/core`, `picocolors`, `sisteransi`뿐이라 작고, ESM이며, select·multiselect·text·confirm·`isCancel`을 제공한다. Windows Terminal·cmd·PowerShell에서 readline keypress로 동작한다. ② `@inquirer/prompts`: 기능은 비슷하지만 하위 패키지가 많아 설치 크기가 몇 배다. ③ ink + react: 자유로운 레이아웃은 장점이지만 react·yoga 레이아웃 엔진 등 의존성이 수십 개이고 JSX 빌드 설정이 필요하다. R65의 "최소 의존성"과 맞지 않는다. 화면 흐름(목록 선택 → 다음 화면 → 뒤로/종료)은 select를 반복하는 상태 기계로 충분하므로 ①을 고른다. 정확한 버전은 구현 시점에 2주 이상 지난 최신판을 lockfile로 고정한다.
- **구조.** `cli/src/lib/prompt.ts`에 `Prompter`, `BACK`/`EXIT` 심볼, `clackPrompter()`(취소 Ctrl-C → `EXIT`), `scriptedPrompter(answers)`, `askerPrompter(asker)`를 둔다. `isInteractive()` = `stdin.isTTY && stdout.isTTY`이고, 테스트에서는 옵션으로 넘긴다. 화면은 `cli/src/commands/config.ts`에 순수 상태 기계로 둔다(`main → models → role → models …`). 화면마다 `(state, prompter) → next`이고, 파일 쓰기는 `configure.ts`의 기존 함수를 재사용한다. 그래서 테스트는 `scriptedPrompter` + fixture repo + `detectVendors`/`modelCache` 주입으로 TTY 없이 돈다.
- **쓰기.** global 모델 → `configureBindings({set})`(파일과 생성물). local 모델 → `configureBindings({local, set})`. ON/OFF(화면과 S-11 플래그 공용) → 새 `setRoleEnabled(root, role, enabled, scope)`. global은 YAML Document API로 해당 키만 바꿔서 주석과 순서를 보존하고 생성물을 다시 만들며, local은 `writeLocal`을 쓴다. global을 다시 켜면 `enabled` 키를 지운다(기본값은 ON). local은 팀 값과 같아지면 키를 지우고, 다르면 `true`/`false`를 그대로 적는다.
- **resolver.** `teamRoles`·`loadLocal`이 `enabled`를 읽는다. `roleMeta`는 `covered_by`를 읽는다. `ResolvedBinding`에 `enabled: boolean`, `covered_by?: string`을 더한다. 꺼진 역할도 모델 해석은 그대로 한다(다시 켤 때 보이도록).
- **install.** `runInstall`의 `asker.ask` 네 곳을 `prompter.vendors(...)`, `.language`, `.gates`, `.subdirGates`의 타입 질문으로 바꾼다. `askerPrompter`는 각 질문을 지금 문자열로 물어 같은 방식으로 파싱한다(기존 install 테스트가 그대로 통과해야 한다). `reins.ts`는 manual + TTY일 때 `clackPrompter`, manual + 비TTY일 때 `askerPrompter(await stdinAsker())`, auto일 때 `askerPrompter(defaultsAsker)`를 고른다.
- **update.** `runUpdate`는 그대로 둔다. `reins.ts`에서 대화형일 때 `runUpdate({dryRun:true})` → 기존 출력 함수로 계획을 출력 → `confirm` → `runUpdate({})` 순서로 부른다. 출력 함수는 action 밖으로 빼서 두 번 쓴다.
- **known 모델 목록.** `knownModels(root, vendor)`를 `bindings.ts`에 순수 함수로 둔다(역할 파일과 bindings에서 모음). 별도 하드코딩 목록은 두지 않는다.
## 우려 표시
- 불변식 "설계서가 기준, 다르면 같은 커밋에서 양판 수정": S-10으로 충족한다. §6 생성 규칙이 바뀌는 것(꺼진 역할은 생성하지 않음)은 설계 변경이므로 같은 커밋에서 양판을 고친다. 충돌 없음.
- R65(배포물은 TypeScript, Python 불필요, 런타임 의존성 최소): `@clack/prompts`는 순수 JS 패키지이고 네이티브 빌드나 Python이 없다. 런타임 의존성은 3개에서 4개(간접 포함 7개)로 는다. 의존성 추가는 intent 영향 범위에 명시되어 있다. 충돌 없음. 다만 매 실행마다 로드되지 않게 `config`·대화형 install·update 경로에서만 동적 `import()` 한다.
- R67(양판): 설계서·README 표와 문장은 양판을 함께 고친다. TUI 화면 문자열은 intent 예시대로 영어(코드)다. 충돌 없음.
- 형식은 추가만: `roles.<r>.enabled`(양 층), 역할 frontmatter `covered_by`, local 스키마의 `roles` 항목 완화(받아들이는 범위만 넓힘), status JSON `enabled`/`covered_by`, `config` 명령, `update --yes`를 더한다. 기존 파일은 그대로 유효하다. 충돌 없음.
- `covered_by`의 배정(S-6)은 intent가 "pm이나 상위 역할"이라고만 해서 planner가 제안했고 pm이 그대로 받았다(2026-10-28). 자기 작업 판정 금지는 사슬 위임으로 지킨다.
- S-11(비대화형 ON/OFF 플래그)은 intent의 비대화형 제약을 근거로 pm이 더했다(2026-10-28). 형식이 아니라 옵션만 추가한다.
- local이 양쪽으로 이기므로(pm 결정) 팀이 끈 역할을 한 사용자가 켤 수 있다. 그 역할에는 생성된 agent 파일이 없어서 스킬이 해석 모델로 직접 부른다(S-7). 팀 생성물은 팀 값만 따르므로 drift는 없다.
- 꺼진 역할(어느 층이든)이 ticket `role:`에 지정돼도 T1은 이번에 WARN만 낸다(pm 결정). 막는 것은 0.2에서 한다.
- CI에는 TTY가 없어서 clack 렌더링을 자동으로 테스트하지 못한다. 그래서 세 OS 수동 시나리오를 검증 기준 C-13에 둔다.
## 검증 기준
- C-1 (S-1) `package.json` dependencies가 `ajv`, `commander`, `yaml`, `@clack/prompts` 넷뿐이다. `config`·install·update 테스트가 `scriptedPrompter`로 TTY 없이 통과하고, `clackPrompter`는 정적 import로 `reins.js` 시작 경로에 들어 있지 않다(vitest, 소스 검사).
- C-2 (S-2) 비TTY에서 `reins config`는 exit 0이고, 출력에 역할마다 해석 줄과 `configure bindings --set` 안내가 있으며, 파일을 하나도 바꾸지 않는다. `--json`은 `bindings` 배열을 낸다. 기존 `configure bindings|gates` 테스트가 그대로 통과한다.
- C-3 (S-3) 스크립트 `[models, scope=global, role planner, vendor claude, claude-opus-5-5, < Configuration, exit]`를 실행하면 `bindings.yaml`의 planner가 바뀌고 `.claude/agents/reins-planner.md`가 다시 만들어진다. scope=local이면 `bindings.local.yaml`만 바뀌고 `bindings.yaml`과 `.claude/`는 바이트 단위로 같다. 화면 목록의 첫 두 항목이 `< Configuration`, `exit`이다.
- C-4 (S-4) global에서 docs를 OFF로 하면 `roles.docs.enabled: false`가 생기고 다른 키와 주석은 그대로다. local OFF는 local 파일에만 쓰인다. pm·implementer·verify-tool을 끄라는 요청은 거절되고, multiselect 선택지에 이 셋이 없다. 팀 OFF + local `enabled: true` → ON(source local), 팀 ON + local `false` → OFF다. 어느 층에 고정 역할 `enabled: false`가 있어도 ON이고 경고가 나온다. `enabled`만 있는 local 항목이 스키마를 통과한다.
- C-5 (S-5) `detectVendors`가 claude·cursor만 감지하면 벤더 목록이 그 둘이다. cursor 선택 시 주입한 `run`의 목록이 나온다. `run`이 실패하면 known 목록과 `other`가 나오고 실패 이유가 출력된다. claude는 known 목록(역할 파일의 claude 모델 포함)과 `other`이고, `other` → text 입력값이 그대로 저장된다. `REINS_NO_VENDOR_SPAWN` 아래에서는 실제 프로세스를 만들지 않는다.
- C-6 (S-6) 모든 역할 파일에 `covered_by`가 있고 고정 세 역할을 빼면 값이 역할 이름, `caller`, `user` 중 하나다. 팀 OFF 역할은 `status --json`에 `enabled: false, covered_by`로, 텍스트에 `off → <role>`로 나온다. reins-loop SKILL.md에 `covered_by` 문단이 있다(문자열 테스트). 꺼진 역할의 ticket에서 T1은 WARN 한 줄을 내고 exit 0이다.
- C-7 (S-7) 팀 OFF 역할은 `generateVendorFiles` 결과에 없고, `configure`·`update` 후 그 agent 파일이 지워진다. local `enabled`(true·false)는 생성 결과를 바꾸지 않는다(바이트 비교). 팀 OFF + local ON 역할은 agent 파일이 없고, `status --json`에는 `enabled: true`와 해석 모델로 나온다. reins-loop에 agent 파일이 없으면 해석 모델로 부르라는 문장이 있다. 이 저장소에서 `check --drift`가 통과한다.
- C-8 (S-8) 비TTY manual install에 지금 테스트의 stdin 줄을 넣으면 결과가 이전과 같다(기존 테스트 통과). scripted TTY install은 벤더 multiselect `[claude, openai]`, 언어 `en`, 게이트 yes, 하위 게이트 하나로 같은 bindings·install.yaml·gates.yaml을 만든다. auto 모드는 prompter를 부르지 않는다.
- C-9 (S-9) scripted 대화형 update에서 confirm no면 파일이 바뀌지 않는다(git status clean). yes면 비대화형 update와 같은 결과다. 계획 출력에 `+`/`~`/`-` 줄과 bindings 이동 줄이 있다. `--yes`나 비TTY에서는 confirm을 부르지 않는다.
- C-10 (S-10) 설계서 양판 §5에 `enabled`·고정 역할·`covered_by`, §6에 꺼진 역할 생성 제외, §9에 `config`·`update --yes`·TUI 비대화형 규칙이 있다. README 양판 Commands 표에 `config` 줄이 있고, reins-setup에 `reins config`가 있다(문자열 테스트).
- C-12 (S-11) 비TTY에서 `configure bindings --disable docs`를 실행하면 `bindings.yaml`에 `enabled: false`가 생기고 agent 파일이 지워진다. `--local --disable docs`는 local 파일만 바꾼다. `--enable docs`는 다시 켠다. `--disable pm`과 `--disable nosuch`는 exit 1이고 파일이 바뀌지 않는다. 설계서 §9와 README Commands 표에 `--enable`·`--disable`이 있다(vitest·문자열 테스트).
- C-13 (S-1·S-3·S-8·S-9, 수동) qa-run이 Linux·macOS·Windows 실제 터미널에서 한 번씩 확인한다. `reins config` 화면 이동(`< Configuration`·`exit`·Ctrl-C), 모델 하나 바꾸기, 역할 하나 끄고 켜기, manual install 화면, update 확인 no/yes. 화면이 깨지거나 키 입력이 안 먹으면 실패다. 결과는 `.loctx/reports/`에 OS마다 남긴다.
- C-11 `pnpm check`가 세 OS × Node 22·24 CI에서 통과하고, `reins check --drift`가 통과한다. 0.1.5 설치 fixture에서 `reins update --yes`를 하면 bindings.yaml·local 파일이 그대로 유효하다.
