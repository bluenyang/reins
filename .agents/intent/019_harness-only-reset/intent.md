## 문제
reins는 프로젝트에 하네스·루프·그래프 엔지니어링을 깔아 주는 도구여야 하는데, 0.1.0부터 작업 중에 불리는 도구로 만들어졌다(감사 두 건, 2026-11-07, `.loctx/reports/2026-11-07_full-audit/`).
- **적용 저장소가 일하는 동안 reins 패키지에 기댄다.** 단계 스킬은 0.1.0부터 `npx @bluenyang/reins@<v>`로 `check`·`gate`·`new`·`status`·`metrics`를 부른다(`0a71780`, 0.1.3에서 버전만 고정). 생성되는 git 훅 줄도 `npx @bluenyang/reins check`다(`b131c6c`). 생성 AGENTS.md 블록은 전환마다 `reins check`를 지시한다. 네트워크가 없으면 루프가 멈추고, 패키지가 오염되면 적용한 모든 저장소에서 그 코드가 돈다. 취소된 0.2.1 브랜치는 여기에 프롬프트·도구 호출마다 도는 런타임 훅과 CLI 소유 단위·승인·감사를 더했다.
- **출발점은 첫 설계다.** 조사한 저장소(AI-GW)는 훅과 CI가 저장소 안의 `scripts/check/*.sh`를 불렀는데, 설계 초안이 이를 "`reins check`가 그 스크립트다"로 바꿨다(`.loctx/context/plan/3_design-doc.draft.md:373-376`). 2026-10-29 "hook에서 npx가 실행? 왜 npx가 쓰이는지 모르겠음. script를 사용하는게 아니었나?"라는 질문은 지연 문제로 바뀌어 처리됐고 답이 돌아가지 않았다.
- **휘발성 파일이 쌓인다.** bus는 0.1.x에서 "에이전트가 지운다"였지만 지워지지 않았고(2026-10-29 기준 닫힌 ticket 26건), 게이트 로그·실행 기록에는 삭제 규칙이 없었다. 정리는 매번 다음 버전으로 밀렸다.
- **에이전트가 하네스와 단계를 따르지 않는다.** 설치된 AGENTS.md는 프로젝트가 쓴 글에 reins 블록 몇 개가 끼어 있을 뿐이어서, 적용 저장소의 에이전트가 단계를 건너뛴다. 이것을 런타임 차단으로 막으려던 것이 0.2.1이다.
- **역할이 많고 다중 에이전트를 전제로 한다.** 역할 12개가 각자 모델에 묶여 있어, 에이전트 하나로 쓰는 경로가 분명하지 않다.

## 바라는 결과
- **reins는 하네스를 관리하는 도구일 뿐이다.** 명령은 install, migrate, update, configure(와 그 TUI)다. 설치가 끝난 뒤 프로젝트가 일하는 동안 어떤 훅도, 어떤 스킬도, 어떤 에이전트도 `reins`나 `npx @bluenyang/reins`를 실행하지 않는다. 설치된 것은 reins와 네트워크 없이 동작한다.
- **단계 검사는 프로젝트가 소유한다.** 필요한 검사는 일반 훅 도구(lefthook, husky)나 프로젝트 안의 독립 스크립트로 둔다. reins는 그것을 설치하거나 제안만 하고, 갱신은 `update`로만 한다.
- **단계를 지켰는지는 감사로 확인한다.** 계획(버전) 하나가 끝날 때마다 감사를 한다. 감사는 AGENTS.md와 하네스 설정 파일(모델 할당과 같은 방식)에 필수로 적고, 사용자가 그 설정으로 직접 끄지 않는 한 빠지지 않는다. 감사는 단계 기록(intent·spec·plan·ticket·리뷰·history)과 git 이력을 읽어 판정하고, 결과를 커밋되는 기록으로 남긴다. 에이전트가 빠뜨리면 사용자가 지적해 바로잡는다는 것도 AGENTS.md에 적는다.
- **역할을 세분화하고 단순하게 한다.** 역할마다 할 일·하지 않을 일이 분명하고, 필수 역할은 적다. 단일 에이전트 하나로 루프 전체가 성립하고, 여러 에이전트는 그 위에 얹는 층이다. 다른 모델이 없을 때 리뷰·감사는 같은 모델이 하되 "독립성 저하"로 기록한다.
- **설치 뒤 첫 대화는 온보딩이다.** install이나 migrate가 끝나면 PM이 첫 대화에서 프로젝트를 파악하고(구조, 스택, 명령, 기존 규칙), 사용자에게 물어 AGENTS.md의 프로젝트 절(목표, 규칙, 관례)을 그 프로젝트에 맞게 쓴다. AGENTS.md의 기본 블록은 하네스 구조와 단계를 강하게 명시해, 차단 없이도 에이전트가 따르게 한다.
- **파일은 만들 때 수명을 정한다.** 하네스가 만드는 파일마다 누가, 언제 지우는지를 함께 정하고, 단계 스킬의 끝 단계에서 지운다. 정리를 다음 버전으로 미루지 않는다.
- **기존 설치를 옮긴다.** 0.1.x·0.2.0 설치를 `update`(또는 `migrate`)가 이 구조로 옮긴다. 스킬·훅·AGENTS.md의 reins 호출을 걷어내고, 쌓인 휘발성 파일은 목록을 보여 준 뒤 사용자가 허락하면 지운다.
- 설계서(`docs/design.md`·`docs/design.ko.md`)를 먼저 이 원칙으로 고쳐 쓰고, 그다음 코드를 고친다.

## 영향 범위
설계서 양판(§0 원칙, §3 검증기, §5 경계, §6 생성물, §9 CLI, §11), `harness/`(roles, policy, schemas, templates, `agents-md-blocks.md`), `skills/`(단계 스킬 전부), `cli/`(generate·install·update·migrate·configure; check·gate·new·status·metrics·retro·knowledge 같은 작업 중 명령의 처리), README 양판, `docs/violations*`, 테스트, 이 저장소의 `.husky/`·CI, 로드맵.

## 제약
- 설치 시점에 npx로 reins를 받는 것은 괜찮다(사용자, 2026-10-25 "push해서 npx로 써보고 싶다"). 작업 시점의 의존과 구분한다.
- 사람의 커밋·작업 방식을 하네스 상태 때문에 바꾸게 하지 않는다(사용자, 2026-10-29 "AI를 위해서 사람이 커밋하기 어렵게 만든다는 거 자체가 이상함").
- 이 저장소도 적용 저장소와 같은 경로를 쓴다. 이 저장소만 `node cli/dist/reins.js`를 부르는 구조가 npx 문제를 가렸다.
- 출시물은 TypeScript다(R65). 파일 형식이 바뀌면 `update`나 `migrate`가 옮긴다.
- 취소된 `feat/loop-enforcement`의 코드는 가져오지 않는다. 문서(역할 정의, 질문 규칙 등)는 이 intent의 원칙에 맞는 것만 다시 쓴다.

### 에이전트가 정한 것
| # | 정한 것 | 대안 | 이유 |
|---|---|---|---|
| 1 | 필수 역할 4개: **pm**(사용자 대화, intent, 로드맵, 온보딩, 계획), **implementer**(구현, 게이트 실행, 커밋), **reviewer**(코드 리뷰와 검증·테스트 판정을 합침), **auditor**(버전 끝 감사). 나머지(planner, pl, qa-design, qa-run, docs, deploy, advisor, lookup)는 선택 역할로, 꺼져 있으면 필수 역할이 맡는다 | 지금 12개 유지 / 더 줄여 3개(리뷰와 감사 합침) | 단일 에이전트에서도 "만든 것"과 "판정하는 것"과 "버전을 감사하는 것"은 단계로 나뉘어야 한다. 감사는 리뷰와 보는 범위(버전 전체, 단계 준수)가 달라 합치지 않는다 |
| 2 | 감사 설정은 `.agents/harness/` 아래 커밋되는 설정 파일(모델 할당과 같은 층)에 `audit: required`로 두고, 끄려면 사용자가 그 값을 바꾼다. 감사 기록은 `.agents/audit/<version>.md`로 커밋한다 | AGENTS.md 문장만 / 로컬 파일 | 사용자가 모델 할당과 같은 성격의 설정이라고 했다. 팀이 공유해야 하므로 커밋되는 층이다 |
| 3 | 이 저장소의 husky 훅은 `pnpm check`(와 프로젝트 스크립트)만 부르고 `reins`를 부르지 않는다. 적용 저장소에 설치하는 훅도 같은 원칙으로, 프로젝트 게이트(`gates.yaml`)를 실행하는 독립 스크립트를 둔다 | reins check를 이 저장소에만 남김 | 이 저장소도 적용 저장소와 같은 경로를 써야 한다(제약) |
| 4 | 지금의 작업 중 명령(check, gate, new, status, metrics, retro, knowledge)은 없애거나, 사용자가 직접 쓰는 보조 명령으로만 남긴다. 어느 쪽인지는 명령마다 spec에서 정하되, 스킬·훅·AGENTS.md가 그 명령을 요구하는 일은 없다 | 모두 삭제 / 모두 유지 | 사용자가 쓰는 관리 명령은 원칙과 충돌하지 않는다. 충돌하는 것은 작업 절차가 reins를 요구하는 것이다 |
| 5 | history는 버전마다 한 파일(그 버전의 결정, 판정, 감사 요약)만 남기고, ticket 단위 기록과 bus·게이트 로그는 ticket이나 버전을 닫는 단계에서 지운다. install·update 로그는 history에 쓰지 않는다 | 지금처럼 ticket마다 영구 / history도 전부 휘발 | 기획 R54는 history를 노하우 저장소로 정했고, 사용자는 "일부"가 휘발성이라고 했다. 버전 요약은 감사와 다음 계획의 입력이 된다 |
| 6 | 0.2.1의 감사·plan-adviser·질문 규칙·기본 AGENTS.md 구조는 생각만 가져오고, CLI·훅에 기대는 부분은 버린다 | 브랜치에서 그대로 가져옴 | 두 감사 모두 해당 코드를 런타임 의존으로 판정했다 |

## 하지 않을 것
- 작업 중 reins를 부르는 어떤 형태(런타임 훅, git 훅의 reins 줄, 스킬의 CLI 호출, dispatcher)도 다시 만들지 않는다.
- 0.2.1~0.2.8의 나머지 항목(작업 등급, 문서 루프, discussion 단계, 예산, 다른 벤더 생성물, 깎기)은 이번에 하지 않는다. 0.3이 끝난 뒤 이 원칙으로 다시 따져 로드맵에 올린다.
- Team Croffle 저장소 적용(0.4).
