## 문제
reins는 프로젝트의 하네스를 깔고 관리하는 도구여야 하는데, 0.1.0부터 작업 중에 불리는 도구로 만들어졌다.
- 단계 스킬과 생성되는 git 훅이 `npx @bluenyang/reins`로 `check`·`gate`·`new`·`status` 등을 부르고, 생성 AGENTS.md는 전환마다 `reins check`를 지시한다. 적용 저장소는 일하는 동안 reins 패키지에 기댄다. 캐시가 없는 오프라인 환경이면 멈추고, 패키지가 오염되면 적용한 저장소가 모두 노출된다. 취소된 0.2.1 브랜치(`feat/loop-enforcement`)는 여기에 프롬프트·도구 호출마다 도는 런타임 훅과 CLI가 소유하는 작업 단위·승인·감사를 더했다.
- 시작은 첫 설계였다. 조사한 저장소는 훅과 CI가 저장소 안의 검사 스크립트를 불렀는데, 설계가 이를 "`reins check`가 그 스크립트다"로 바꿨다. 2026-10-29에 사용자가 "hook에서 npx가 실행? … script를 사용하는게 아니었나?"라고 물었지만 지연 문제로 바뀌어 처리됐다.
- 휘발성 파일(bus, 게이트 로그, 실행 기록)은 일부만 지워졌고, 생성물 전체의 수명 관리가 없었다.
- 역할 12개는 목표가 부정확하고 추상적이었고, 다중 에이전트를 전제로 해 단일 에이전트로 쓰는 길이 분명하지 않았다. 설치된 AGENTS.md는 단계를 충분히 명시하지 않아 에이전트가 하네스를 건너뛴다.

근거 기록(로컬): 감사 두 건 `.loctx/reports/2026-11-07_full-audit/`, 요구 논의 `.loctx/reports/2026-11-08_roles-discussion/owner-notes.md`, 요구사항 정리본 `.loctx/context/plan/v0.3_requirements.md`(3판, 사용자 검토 2026-11-09).

## 바라는 결과
### reins와 프로젝트의 경계
- reins의 명령은 `install`, `migrate`, `update`, `config`(지금의 `configure`를 통합)뿐이다. 작업 중 쓰던 명령(`check`, `gate`, `new`, `status`, `metrics`, `retro`, `knowledge` 등)은 없앤다.
- 설치가 끝난 뒤 프로젝트가 일하는 동안 어떤 훅·스킬·에이전트도 `reins`나 `npx @bluenyang/reins`를 실행하지 않는다. 설치된 하네스는 reins와 네트워크 없이 동작한다. 설치 시점에 npx로 reins를 받는 것은 괜찮다.
- 단계 검사는 프로젝트가 소유한다: lefthook·husky 같은 훅 도구나 프로젝트 안의 스크립트. install은 할 수 있는 만큼 제안·설정하고, 훅 도구가 없으면 첫 세팅에서 PM이 묻거나 사용자 지시대로 세팅한다.
- `config`: 단순/상세 모델 할당 모드, 역할군별·상세 역할별 모델, 에이전트 툴(claude, codex, agy, gemini, copilot, cursor agent 등) 다시 감지와 사용 여부, 단일/멀티 전환, 로컬 덮어쓰기. 역할군을 켤 때 켤 만한 조건을 보여 준다.

### 역할
- 모델 할당은 "이 일을 어느 벤더의 어느 모델이 하느냐"이지 에이전트 수가 아니다. 상속은 상세 역할 > 역할군 > 기본값(꺼짐 = PM이 함). vendor와 model은 한 묶음으로 상속하고, 실행 중 해석이 필요한 필드(`escalation`, `limits`, `parallel`)는 없앤다.
- **단일이 기본이다.** 역할군에 모델을 할당하지 않으면 그 일은 PM이 한다. 단일 모드에도 상시 위임 구조는 없지만, PM은 읽기 위주의 일(조사, 큰 로그 요약, 리뷰, 감사)과 급할 때 서로 독립인 기능의 병렬 구현에 같은 모델의 서브에이전트를 쓸 수 있다. 계획과 구현처럼 이어지는 일은 한 실행이 이어서 한다. 근거: Anthropic, "Building agents: When to fold subagents into your main agent loop"(2026-10-22), "Building multi-agent systems: When and how to use them"(2026-01-23).
- 멀티의 역할군(PM 말고는 모두 선택):
  - **PM**: 사용자(PO)와 대화, 핵심은 묻고 나머지는 스스로 판단, intent 작성(방향성과 계획; plan.md는 intent로 합침), 지시와 재배정. 모든 보고는 PM을 거친다. 하위 역할은 상위 모델을 직접 부르지 않고 사유를 붙여 PM에게 돌려보낸다.
  - **PL**: 작업 관제(선택; 병렬 작업이나 PM 컨텍스트 저하 때), 리뷰(Plan-Reviewer, Code-Reviewer, QA-Plan-Reviewer, Document-Reviewer, Retrospector; 일상 리뷰는 리뷰어 하나), Discussion(큰 결정·이견 때 할당 모델 전부가 서로 보지 않고 의견, PM이 원문을 붙여 종합). 모델이 여럿이면 하나가 관제이고, 관제 모델의 리뷰 참여는 독립 리뷰로 친다.
  - **Planner**: spec-writer(확정 intent → spec, 작업 단위 분할), qa-designer(테스트 방법·체크리스트; 코드를 볼 수 있다).
  - **Implementer**: 코드, 테스트 코드, 문서(로드맵 둘, README 등 표준 문서, `.loctx` 문서; 문서 언어는 입력값). 같은 기능의 코드·테스트·문서는 한 실행이 이어서 처리할 수 있다.
  - **Executor**: Tool-Executor(툴 실행 로그를 취합해 PL에게; 큰 로그일 때만), Researcher, QA-Runner, Deployer(stable은 항상 사용자 지시).
  - **Advisor · Committee**: 고지능 모델 여럿. 복잡하거나 추상적인 요구, 절차 미준수 같은 큰 문제의 해결안.
  - **Auditor**: 독립 군, 하나. 하네스와 엔지니어링 기법만 근거로 감사한다.
- 도구 권한(쓰기, 셸, push)은 상세 역할 파일마다 고정한다. Look-up은 Retrospector로 이름을 바꾼다.
- PM이 위임할 때 넘길 파일과 결정 목록을 지시문에 적고, 하위 역할은 받은 것 밖의 추정을 표시한다.

### 흐름, 감사, 승인, 회고
- 흐름: `ROADMAP.local.md`(아이디어) → 사용자와 정리 → `ROADMAP.md` → intent → 승인 → spec → 승인 → 구현·커밋 → 테스트 → 머지 → 감사 → rc → (stable) → 회고 → 휘발성 파일 정리.
- 단계 스킬: `onboard`, `roadmap`, `intent`, `spec`, `implement`, `review`, `test`, `merge`, `audit`, `release`, `retro`. 접두어 없음, 지휘자 스킬 없음. 순서는 AGENTS.md 기본 블록이 갖고 각 스킬 끝에 다음 스킬을 적는다. 스킬마다 "위임" 문단 하나로 단일·멀티가 같은 스킬을 쓴다. 스킬마다 그 단계가 만든 파일과 수명을 적는다. 스킬은 평문이고 reins를 부르지 않는다.
- 감사: 머지 뒤, rc 전. 그 시점의 AGENTS.md와 하네스 설정, intent, spec, 로드맵 둘, git 이력, history, 게이트·테스트 로그를 읽고 흐름을 지켰는지, 생성 파일·하네스 파일이 손으로 바뀌지 않았는지 판정한다. 각 행위 당시의 규칙을 기준으로 한다. 증거 경로가 없으면 통과가 아니라 "확인 불가"다. 사용자 지시로 건너뛴 단계·승인은 그 자리에서 기록하고 감사는 넘기되, 다음 루프는 지시 없이 따른다. 위반은 보완하거나 사용자가 받아들이고, 어느 쪽이든 감사와 회고에서 정확히 비판하며 경중에 따라 PL이나 Advisor 의견으로 해결 방법을 낸다. 결과는 `.agents/audit/<단위>.md`로 커밋한다. 감사는 사용자가 하네스 설정으로 끄지 않는 한 필수이고, AGENTS.md가 그 설정을 가리킨다. 버전 종료 보고에 감사 상태를 넣는다. 단일 모드 감사의 세션과 모델은 사용자가 고른다(권장: 새 실행 + 다른 벤더, 또는 새 실행 + 같은 벤더 최상급 모델).
- 승인: PM이 사용자 말을 인용해 intent·spec에 `approved: {by, at, words}`를 적고 커밋한다. 승인 기록은 승인 대상의 개정을 가리킨다. 사용자가 원하면 직접 한다. spec 요약은 매번 진행/수정을 기다린다.
- 리뷰와 자기 리뷰: spec 항목 ↔ 커밋 ↔ 증거 경로 대조표를 채우고 결함도 찾는다. 자기 리뷰는 독립 검토가 아니라고 적는다. Plan-Reviewer는 사용자 원문, 승인된 intent, 제품 경계를 spec과 대조한다.
- 회고: stable 뒤(stable을 내지 않는 버전은 사용자가 종료를 선언하면). 감사 결과와 릴리스 과정을 보고 Retrospector가 AGENTS.md·스킬·하네스 개선안을 낸다. "켠 역할군이 값을 했는가"를 본다. 사용자가 받아들인 것만 반영한다: 프로젝트 절과 knowledge는 PM이, 하네스 원본은 `config`·`update`로.
- 단일 모드에서도 감사와 큰 결정에는 사용자가 별도 세션이나 다른 벤더로 외부 검토를 요청할 수 있다.

### 설치, 온보딩, 파일 수명, 이전
- install·migrate는 AGENTS.md에 온보딩 표시를 남긴다. 다음 첫 대화에서 PM이 프로젝트를 파악하고 사용자에게 물어 프로젝트 절(목표와 범위, 스택과 명령, 기존 규칙과 관례, 금지선, 문서 언어)을 쓰고, 끝나면 지시를 지우거나 "완료됨"으로 표시한다. install의 기본 모드는 단일이다.
- migrate에서 AGENTS.md가 충돌하거나 단일/멀티를 바꾸면, 기존과 신규를 둘 다 두되 한쪽은 참고 자료로 분리하고 다음 첫 대화에서 PM이 합친다. 모드를 바꿀 때 진행 중인 작업의 재개 지점을 남긴다.
- AGENTS.md 기본 블록은 하네스 구조와 흐름을 강하게 명시한다(차단 없이 따르게).
- 하네스가 만드는 파일마다 누가·언제 지우는지를 만들 때 정한다. 작업 중 기록(ticket, 하위 보고, 게이트·테스트 로그)은 회고 뒤 정리 때 지우고, 지우기 전에 대상 커밋·검증 결과·예외·감사 근거를 history나 감사 기록에 요약한다. history는 버전마다 한 장(결정, 판정, 건너뛴 단계, 감사·회고 요약)이고, install·update 로그는 history에 쓰지 않는다.
- `update`는 손으로 고친 생성 파일을 덮어쓰기 전에 보여 주고 확인받는다.
- 기존 0.1.x·0.2.0 설치는 `update`로 0.3 구조로 옮긴다. 스킬·훅의 reins 호출을 걷어내고, AGENTS.md는 충돌로 처리하며, 쌓인 `.loctx` 휘발성 파일은 목록을 보여 주고 확인 뒤 지운다. 기존 사용자 훅과 설정은 보존한다.

## 계획
작업 순서. 각 항목은 spec에서 작업 단위로 나눈다.
1. **이 저장소의 운영 전환.** 0.2.0 하네스를 걷어낸다: husky 훅은 `pnpm check`만 부르고, AGENTS.md의 reins 블록과 작업 중 명령 지시를 빼고 이 intent의 흐름을 손으로 따른다고 적는다. 0.3 개발 동안 단일 모드 + 큰 결정에 외부 검토로 운영해 단일 모드 설계를 시험한다.
2. **설계서 재작성.** `docs/design.ko.md`와 영어판을 이 intent로 고쳐 쓴다(원칙, 경계, 역할, 흐름, 감사, 생성물, 명령, 파일 수명). 기획서 요구 가운데 바뀌는 것(R53 등)도 같은 변경에서 고친다. 코드는 그다음이다.
3. **하네스 원본.** `harness/roles`(역할군과 상세 역할, 권한), 설정 파일 형식(모델 할당 후속, 감사 on/off), templates(intent·spec·감사·history), AGENTS.md 기본 블록(흐름, 온보딩 표시, 설정 파일 위치).
4. **단계 스킬 11개.** 평문, 위임 문단, 다음 스킬, 만든 파일과 수명.
5. **CLI.** 작업 중 명령 제거, `configure` → `config` 통합과 새 항목, 생성기(훅 생성 대신 제안·설정, reins 호출 없는 생성물), `update`의 이전과 덮어쓰기 확인, install의 온보딩 표시와 기본 단일 모드.
6. **테스트와 검증.** 생성물 어디에도 `reins`·`npx @bluenyang/reins` 실행이 없다는 검사, 0.1.x·0.2.0 설치본을 보존한 별도 사례에서 이전 검증(기존 훅·설정 보존, reins 호출 제거, 중단 뒤 다시 실행), 이 저장소의 자기 이전.
7. **문서.** README 양판, `docs/violations*`, CHANGELOG.

## 제약
- 출시물은 TypeScript다(R65). 파일 형식이 바뀌면 `update`나 `migrate`가 옮긴다.
- 사람의 커밋·작업 방식을 하네스 때문에 바꾸게 하지 않는다(사용자, 2026-10-29).
- 취소된 `feat/loop-enforcement`의 코드는 가져오지 않는다.
- 설계서를 먼저 고치고 코드를 고친다.
