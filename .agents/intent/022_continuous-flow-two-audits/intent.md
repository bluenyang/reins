## 문제
0.3.1(intent 021)을 만들면서 지금 하네스의 흐름에 빈 곳이 드러났다(사용자 "나는 지금 조금씩 구멍이 보이는 것 같거든?"). 배경은 `docs/conversation/2026-11-11_flow-audit-agents-md.md`에 있다. 이 intent의 첫 초안은 0.3.1의 stable과 회고 전에 쓰였고(아래 여섯째 문제가 그 일이다), 회고 뒤 그 원인을 분석한 다음 다시 썼다.

- **작은 spec 조정도 멈추고 승인받게 되어 있다.** `implement` 스킬과 흐름 블록은 작업 단위가 바뀌면 크기와 상관없이 멈추고 진행/수정을 받게 한다. 그래서 리뷰에서 나온 작은 보완까지 "승인 없는 변경"으로 감사에 잡혔다(021 감사 비판 1·3, A1).
- **승인 뒤에도 계속 묻는다.** 푸시와 PR이 "기계를 떠나는 일"로 묶여 매번 허락을 구한다. reins를 쓰는 다른 프로젝트에서도 intent와 spec을 승인한 뒤 승인 요청이 이어진다.
- **감사가 한 번이고 머지 뒤다.** 큰 문제가 있어도 머지를 막지 못한다. 보완 커밋을 다시 감사할지에 대한 기준이 없어 021에서는 감사를 두 번 받았고, 두 번째는 보완 과정의 절차 지적을 새로 냈다.
- **반복해서 수용되는 지적을 다룰 방법이 없다.** 감사는 다 잡아내는 것이 맞지만, 매번 수용되는 같은 지적이 매번 위반으로 나온다.
- **AGENTS.md에 현재 진행 상황이 적힌다.** 에이전트는 세션마다 이 파일을 읽으므로 끝난 작업의 내용까지 계속 읽게 되고, 팀 파일이 자주 바뀌어 충돌이 난다. 온보딩은 프로젝트 절을 "채우라"고만 하고 무엇을 넣고 무엇을 넣지 않는지의 가이드가 없다.
- **버전과 버전 사이의 경계가 없다.** 0.3.1-rc.1을 배포한 직후, stable과 회고 전에 PM이 이 intent의 초안을 썼다(사용자 "배포하고 나면 좀 흐름을 끊으면 안될까? 세션을 바꿔야하는데 바로 intent를 쓰면 언제 해. 회고도 아직 안했잖아"). 분석(위원회 두 의견 포함)의 결론: 흐름은 한 버전 안의 순서만 말한다. `roadmap` 스킬은 버전이 정해지면 `intent`로 넘기라 하고, `intent` 스킬의 시작 조건은 "확정된 로드맵 항목에 승인된 intent가 없다"뿐이며, 정지 목록에 "배포 뒤"가 없다. 그 위에서 PM은 "어느 버전인가"에 대한 사용자의 답을 "시작하라"로 읽었고, 배포가 사용자의 승인을 기다리는 시간을 다음 버전의 일로 채웠다. 회고 전에 쓴 초안에는 회고에서 나온 것이 들어 있지 않았다.
- **머지 주변의 관례가 이 저장소에만 있다.** 머지 지시를 어떻게 읽는지, 머지한 브랜치를 언제 지우는지, 머지 뒤 바뀐 SHA를 기록에 어떻게 적는지는 이 저장소의 AGENTS.md와 PM의 메모에만 있다. 다른 프로젝트에 reins를 적용하면 같은 일이 다시 난다(사용자 "다른 프로젝트에 reins를 적용하면, 몇가지 주요한 하네스는 같이 적용되었으면 하거든").
- **작은 결함 둘(0.3.1 회고).** 테스트만 고친 작업 단위가 리뷰 없이 지나갔다(021 W-10). `update` 보고는 이미 있던 생성 파일을 다시 쓸 때도 새 파일(+)로 표시한다.

## 바라는 결과
- **승인 뒤는 하나의 흐름.** intent 승인과 spec의 진행/수정은 지금처럼 매번 명시적으로 받는다. spec이 수락되면 구현 → 리뷰 → 테스트 → 푸시 → PR → CI → 1차 감사까지 묻지 않고 이어 간다. 멈추고 묻는 것은 되돌릴 수 없는 일, 금지선, 같은 단위의 두 번 실패, 중요한 spec 변경, 머지, stable 릴리스다.
- **작업 중 spec 조정.** 작업 단위의 추가·삭제나 범위 변경은 멈추고 spec을 고쳐 승인받는다. 같은 단위 안의 방법 변경, 리뷰·감사에서 나온 작은 보완, 비슷한 선례가 기록에 있는 조정은 진행하고, spec에 적은 뒤 그 흐름의 끝 보고에 모아 알린다. spec에는 조정 기록을 두는 자리가 있다(무엇을, 왜, 어느 커밋에서).
- **감사 두 번.**
  - 1차: CI가 통과한 뒤, 머지 전에. PR 브랜치를 보고 위험을 본다 — 승인 없는 범위 확장, 금지선, 생성·하네스 파일 손 수정, 리뷰 빠진 단위, 실패한 검사. 위반은 머지 전에 보완하거나 사용자가 수용한다. 문제가 없거나 처리가 끝나면 PM은 결과를 보고하고, 사용자의 머지 지시를 받으면 바로 머지한다(사용자 "머지는 감사 이후 문제가 없으면 승인받고 바로 했으면 좋겠는데").
  - 2차: 머지와 배포 뒤에. 절차만 본다 — 머지 지시와 방식, CI·배포 기록, 릴리스 문서, 기록의 완결성. 고치라는 명령을 내지 않고 결과를 회고로 넘긴다.
  - 감사는 이력을 훑어 문제를 찾고 시정할 것을 말한다. 커밋 하나하나를 규칙 문장과 대조하는 방식으로 쓰지 않는다.
  - 기록·문서 보완은 다시 감사하지 않는다. 위험이 큰 문제가 있었고 변경이 클 때만 다시 받는다.
- **수용된 지적.** 반복되고 매번 수용된 지적을 회고에서 knowledge에 "수용된 지적"으로 올린다(사용자 승인, 기존 승격 절차). 감사는 knowledge를 읽고 그런 지적을 위반 대신 "알려진 수용"으로 표시한다.
- **AGENTS.md 가이드와 온보딩.** 가이드가 AGENTS.md에 두는 것(프로젝트가 무엇인지, 거시적 목표, 구조, 공통 규칙·관례, 금지선, 중요한 지시)과 두지 않는 것(현재 작업, 진행 상황, 버전별 계획, 일회성 결정, 개인 메모)을 말한다. `onboard` 스킬은 사용자와 대화하며 기존 AGENTS.md·CLAUDE.md의 내용을 가린다: 진행 상황·계획은 로드맵으로, 결정과 이유는 knowledge 후보로, 개인 메모는 `.loctx`로, 기여 방법은 CONTRIBUTING으로. 무엇을 어디로 보냈는지 사용자에게 보여 준다.
- **버전의 경계.** 한 버전의 흐름은 배포에서 끊긴다.
  - 배포(rc든 stable이든)를 내면 PM은 보고하고 멈춘다. 배포가 사용자를 기다리는 동안(승인, 2FA) 다른 버전의 일로 채우지 않는다. 같은 버전의 안정화(rc에서 찾은 결함)는 그 버전의 일이다.
  - 회고가 버전을 닫는다. 회고가 끝나면 PM은 닫혔다고 보고하고 멈춘다.
  - 다음 버전의 intent는 회고 뒤, 사용자가 시작하라고 할 때 쓴다. 버전을 고른 것("0.3.2가 낫겠다")은 시작 지시가 아니다.
  - 다음 버전의 아이디어는 언제든 로드맵에 적는다. 잃지 않되 기다린다.
  - 사용자가 회고 전에 다음 intent를 쓰라고 하면 지금의 waiver(한 번)로 적고 한다.
- **머지와 리뷰의 관례를 하네스로**(무엇을 올릴지는 열린 질문 1).
- **작은 결함 둘.** `review` 스킬은 테스트만 고친 단위도 리뷰하거나, 하지 않았다고 기록하게 한다. `update` 보고는 다시 쓴 기존 파일을 새 파일로 표시하지 않는다.
- 설계서 양판(§3 흐름·멈춤·감사, §4 파일, §5 AGENTS.md, §8 knowledge), README 양판, `harness/CHANGELOG.md`가 같은 말을 한다.

## 계획
1. spec: 승인되면 `spec.md`를 쓰고 검토한 뒤 요약에 진행/수정을 받는다. 작업 단위 초안:
   - W-1 승인 뒤의 연속 흐름과 정지 조건(흐름·정지 블록, `implement`·`review`·`test`·`merge` 스킬, 설계 §3-1·§3-2)
   - W-2 작업 중 spec 조정(spec 템플릿의 조정 기록 자리, `spec`·`implement` 스킬, 설계 §3-1)
   - W-3 감사 두 번과 1차 감사 뒤의 머지(`audit` 스킬, auditor 역할, 감사 템플릿, 흐름 블록의 순서, `merge`·`release`·`retro` 스킬, 설계 §3-3)
   - W-4 수용된 지적(knowledge 템플릿, `retro`·`audit` 스킬, 설계 §8)
   - W-5 AGENTS.md 가이드와 온보딩(가이드 문서, `onboard` 스킬, 온보딩·재구성 표시 문장, 설계 §5)
   - W-6 버전의 경계(흐름·정지 블록, `release`·`retro`·`roadmap`·`intent` 스킬, 설계 §3-1·§3-2)
   - W-7 머지·리뷰의 관례(`merge`·`review` 스킬; 열린 질문 1의 답대로)
   - W-8 `update` 보고의 표시(`cli/src/commands/update.ts`와 테스트)
2. 구현 → 리뷰(GPT-6.1 Sol) → 테스트 → PR → CI까지 이어서 한다. 이 버전은 사용자가 말한 방식으로 일한다(설치된 0.3.1 규칙과 다른 곳은 보고에 밝힌다).
3. 1차 감사(GPT-6 Astra) → 머지(사용자 지시) → 0.3.2-rc.1 → 멈춤 → stable(사용자 지시) → 2차 감사 → 이 저장소 자기 업데이트 → 회고 → 멈춤.

## 제약
- reins는 작업 중에 불리지 않는다. 바뀌는 것은 하네스의 글(블록, 스킬, 역할, 템플릿)과 그것을 쓰는 명령이다.
- 차단 장치를 더하지 않는다(0.3 원칙). 흐름을 느슨하게 하는 대신 1차 감사가 머지 앞에 서고, 버전의 경계는 글로만 세운다.
- intent 승인, spec의 진행/수정, 머지 지시, stable 지시는 그대로 명시적이다.
- 감사자는 읽기 전용·오프라인이다(0.3.1).
- 기존 설치는 `update`로 새 블록과 스킬을 받는다. 프로젝트 절(사용자가 쓴 AGENTS.md 본문)을 reins가 고치지 않는다.
- 하네스의 글은 어느 에이전트·어느 저장소에서도 맞아야 한다. 특정 도구에만 해당하는 말(Claude Code auto 모드의 머지 거부 등)은 넣지 않는다.

## 열린 질문
1. **이 저장소의 관례 가운데 무엇을 하네스로 올릴까**(사용자 "그건 다음 버전에서 판단하자"). 하네스로 올리면 reins를 설치한 모든 프로젝트의 스킬에 그 말이 들어간다. PM 안:

   | 관례 | PM 안 | 이유 |
   |---|---|---|
   | 머지 지시 읽는 법 — PR을 지명하면 가장 좋고, 지명이 없으면 열린 PR이 하나일 때 그 PR, 또는 PM이 함께 머지하자고 제안한 묶음. "계속해"는 머지 지시가 아님 | 올림(`merge` 스킬) | 어느 프로젝트에서나 같은 물음이 생긴다 |
   | 머지한 브랜치는 머지 단계에서 원격·로컬 모두 지움 | 올림(`merge` 스킬) | 0.3.1에서 두 번 지적받음. 저장소와 상관없다 |
   | 머지가 SHA를 바꾸면(rebase·squash) 기록은 기본 브랜치의 SHA를 적음 | 올림(`merge` 스킬, 조건문으로) | 감사가 기록의 SHA로 커밋을 찾는다 |
   | 목표 절에 진행 상황을 적지 않음 | 올림 — W-5의 가이드에 이미 들어감 | — |
   | 머지를 다른 명령과 묶지 않고 따로 실행 | 올리지 않음 | Claude Code auto 모드에만 해당 |
   | 커밋 메시지 형식, 기록 커밋은 제목만 | 올리지 않음 | 프로젝트마다 형식이 다르다. 하네스는 "작업 단위를 적는다"까지만 말한다 |
   | `docs/conversation/` 쓰는 법, 문서 언어 쌍 | 올리지 않음 | 이 저장소의 문서 방침 |

### 에이전트가 정한 것
| # | 정한 것 | 대안 | 이유 |
|---|---|---|---|
| 1 | 여덟 가지를 intent 하나로 | 흐름·감사·AGENTS.md를 따로 | 같은 대화와 같은 회고에서 나온 한 묶음이고 같은 블록·스킬을 함께 고친다. 되돌리는 단위는 W-n으로 나눈다 |
| 2 | 작은 조정은 spec에 적고 흐름 끝에 모아 보고 | 조정마다 바로 알림 | "진행 후 보고한다". 조정마다 알리면 다시 묻는 흐름이 된다 |
| 3 | 1차 감사 기록은 PR 브랜치에 커밋해 함께 머지 | 머지 뒤 따로 커밋 | 기록 커밋을 위한 PR이 하나 더 생기지 않는다(021에서는 감사 기록 PR이 더 필요했다) |
| 4 | 2차 감사의 결과는 같은 감사 파일의 둘째 절로, 사용자 처리 없이 회고가 읽음 | 별도 파일 | 버전당 감사 파일 하나(설계 §4) |
| 5 | AGENTS.md 가이드는 하네스의 문서로 두고 `onboard` 스킬이 가리킴 | AGENTS.md 블록에 넣음 | AGENTS.md 자체를 길게 만들지 않는다. 가이드는 쓸 때만 읽으면 된다 |
| 6 | 2차 감사는 stable 배포 뒤, 회고 직전에 한 번 | rc마다 | "그 결과는 그대로 회고로 넘겨서". 그 버전의 머지·rc·stable을 한꺼번에 본다. stable 없이 닫는 버전은 닫는다고 한 때 |
| 7 | `update`로 0.3.2를 받은 기존 설치에 "AGENTS.md를 가이드에 맞게 정리하라"는 표시를 한 번 남김 | 새 설치·이전에만 적용 | 진행 상황이 적힌 AGENTS.md는 이미 설치된 저장소에 있다. 지금의 재구성 표시와 같은 방식이고, 정리는 PM이 사용자와 한다 |
| 8 | 수용된 지적의 기준은 세 번 | 네 번 | "서너번 이상". 회고가 세어 제안하고, 올리는 것은 사용자가 받아들일 때뿐이다 |
| 9 | 회고 뒤에는 사용자의 시작 말을 기다림 | 회고가 끝나면 PM이 `roadmap`으로 넘어가 다음 버전을 물음(지금 글; 위원 한 명의 안) | "세션을 바꿔야하는데". 0.3.1("0.3.1 준비")도 이번도 사용자가 시작을 말했다. 다른 위원의 안과 같다 |
| 10 | 이미 확정된 다음 버전의 항목은 회고 전에도 공개 로드맵에 올릴 수 있음 | 회고 뒤에만 | 로드맵은 계획의 기록이고 일의 시작이 아니다. 막는 것은 intent다. 위원 의견이 갈린 곳(한 명은 "버전 이름만으로는 확정이 아니다") — `roadmap` 스킬에 그 문장을 더한다 |

## 하지 않을 것
- git 저장소가 아닌 작업 폴더 지원(0.4 후보).
- 훅·CI에서 흐름을 막는 장치, 감사 결과를 세는 CLI.
- intent·spec 승인의 자동 수락, 머지·stable의 자동 실행.
- 배포 뒤 세션을 반드시 바꾸게 하는 규칙(멈추고 보고하는 데까지; 세션은 사용자가 정한다).
- reins가 프로젝트의 AGENTS.md 본문을 자동으로 고치거나 옮기는 것(가리는 일은 PM이 사용자와 한다).
- cursor의 `agent` 명령 감지(0.4 후보).
