## 문제
0.3.1(intent 021)을 만들면서 지금 하네스의 흐름에 빈 곳이 드러났다(사용자 "나는 지금 조금씩 구멍이 보이는 것 같거든?"). 배경과 사용자의 말은 `docs/conversation/2026-11-11_flow-audit-agents-md.md`에 있다.

- **작은 spec 조정도 멈추고 승인받게 되어 있다.** `implement` 스킬과 흐름 블록은 작업 단위가 바뀌면 크기와 상관없이 멈추고 진행/수정을 받게 한다. 그래서 리뷰에서 나온 작은 보완까지 "승인 없는 변경"으로 감사에 잡혔다(021 감사 비판 1·3, A1).
- **승인 뒤에도 계속 묻는다.** 푸시와 PR이 "기계를 떠나는 일"로 묶여 매번 허락을 구한다. reins를 쓰는 다른 프로젝트에서도 intent와 spec을 승인한 뒤 승인 요청이 이어진다.
- **감사가 한 번이고 머지 뒤다.** 큰 문제가 있어도 머지를 막지 못한다. 보완 커밋을 다시 감사할지에 대한 기준이 없어 021에서는 감사를 두 번 받았고, 두 번째는 보완 과정의 절차 지적을 새로 냈다.
- **반복해서 수용되는 지적을 다룰 방법이 없다.** 감사는 다 잡아내는 것이 맞지만, 매번 수용되는 같은 지적이 매번 위반으로 나온다.
- **AGENTS.md에 현재 진행 상황이 적힌다.** 에이전트는 세션마다 이 파일을 읽으므로 끝난 작업의 내용까지 계속 읽게 되고, 팀 파일이 자주 바뀌어 충돌이 난다. 온보딩은 프로젝트 절을 "채우라"고만 하고 무엇을 넣고 무엇을 넣지 않는지의 가이드가 없다.

## 바라는 결과
- **승인 뒤는 하나의 흐름.** intent 승인과 spec의 진행/수정은 지금처럼 매번 명시적으로 받는다. spec이 수락되면 구현 → 리뷰 → 테스트 → 푸시 → PR → CI까지 묻지 않고 이어 간다. 멈추고 묻는 것은 되돌릴 수 없는 일, 금지선, 같은 단위의 두 번 실패, 중요한 spec 변경, 머지, stable 릴리스다. AGENTS.md의 흐름·정지 블록과 `implement`·`review`·`test`·`merge` 스킬이 이렇게 말한다.
- **작업 중 spec 조정.** 작업 단위의 추가·삭제나 범위 변경은 멈추고 spec을 고쳐 승인받는다. 같은 단위 안의 방법 변경, 리뷰·감사에서 나온 작은 보완, 비슷한 선례가 기록에 있는 조정은 진행하고, spec에 적은 뒤 그 흐름의 끝 보고에 모아 알린다. spec에는 조정 기록을 두는 자리가 있다(무엇을, 왜, 어느 커밋에서).
- **감사 두 번.**
  - 1차: CI가 통과한 뒤, 머지 전에. PR 브랜치를 보고 위험을 본다 — 승인 없는 범위 확장, 금지선, 생성·하네스 파일 손 수정, 리뷰 빠진 단위, 실패한 검사. 위반은 머지 전에 보완하거나 사용자가 수용한다.
  - 2차: 머지와 배포 뒤에. 절차만 본다 — 머지 지시와 방식, CI·배포 기록, 릴리스 문서, 기록의 완결성. 고치라는 명령을 내지 않고 결과를 회고로 넘긴다.
  - 감사는 이력을 훑어 문제를 찾고 시정할 것을 말한다(사용자 "이력을 훑고, 시정조치 명령을 주는거지"). 커밋 하나하나를 규칙 문장과 대조하는 방식으로 쓰지 않는다.
  - 기록·문서 보완은 다시 감사하지 않는다. 위험이 큰 문제가 있었고 변경이 클 때만 다시 받는다.
- **수용된 지적.** 세 번 이상 반복되고 매번 수용된 지적을 회고에서 knowledge에 "수용된 지적"으로 올린다(사용자 승인, 기존 승격 절차). 감사는 knowledge를 읽고 그런 지적을 위반 대신 "알려진 수용"으로 표시한다.
- **AGENTS.md 가이드와 온보딩.** 가이드가 AGENTS.md에 두는 것(프로젝트가 무엇인지, 거시적 목표, 구조, 공통 규칙·관례, 금지선, 중요한 지시)과 두지 않는 것(현재 작업, 진행 상황, 버전별 계획, 일회성 결정, 개인 메모)을 말한다. `onboard` 스킬은 사용자와 대화하며 기존 AGENTS.md·CLAUDE.md의 내용을 가린다: 진행 상황·계획은 로드맵으로, 결정과 이유는 knowledge 후보로, 개인 메모는 `.loctx`로, 기여 방법은 CONTRIBUTING으로. 무엇을 어디로 보냈는지 사용자에게 보여 준다.
- 설계서 양판(§3 흐름·멈춤·감사, §4 파일, §5 AGENTS.md, §8 knowledge), README 양판, `harness/CHANGELOG.md`가 같은 말을 한다.

## 계획
1. spec: 승인되면 `spec.md`를 쓰고 검토한 뒤 요약에 진행/수정을 받는다. 작업 단위 초안:
   - W-1 승인 뒤의 연속 흐름과 정지 조건(흐름·정지 블록, `implement`·`review`·`test`·`merge` 스킬, 설계 §3-1·§3-2)
   - W-2 작업 중 spec 조정(spec 템플릿의 조정 기록 자리, `spec`·`implement` 스킬, 설계 §3-1)
   - W-3 감사 두 번(`audit` 스킬, auditor 역할, 감사 템플릿, 흐름 블록의 순서, `merge`·`release`·`retro` 스킬, 설계 §3-3)
   - W-4 수용된 지적(knowledge 템플릿, `retro`·`audit` 스킬, 설계 §8)
   - W-5 AGENTS.md 가이드와 온보딩(가이드 문서, `onboard` 스킬, 온보딩·재구성 표시 문장, 설계 §5)
2. 구현 → 리뷰(GPT-6.1 Sol) → 테스트 → PR → CI까지 이어서 한다. 이 버전부터 사용자가 말한 방식으로 일한다(설치된 규칙과 다른 곳은 보고에 밝힌다).
3. 1차 감사(GPT-6 Astra) → 머지(사용자 지시) → 0.3.2-rc.1 → 2차 감사 → stable(사용자 지시) → 이 저장소 자기 업데이트 → 회고.

## 영향 범위
`harness/templates/agents-md-blocks.md`(흐름·정지·기록 블록), `harness/templates/{spec,audit,knowledge}.md`, 새 가이드 문서(위치는 spec), `skills/{spec,implement,review,test,merge,audit,release,retro,onboard}/SKILL.md`, `harness/roles/{auditor,pm,pl}.md`, `cli/src/lib/agents-md.ts`(블록·표시 문장), `cli/src/commands/{install,migrate,update}.ts`(해당되면), `docs/design.md`·`design.ko.md`, README 양판, `harness/CHANGELOG.md`, 테스트.

## 제약
- reins는 작업 중에 불리지 않는다. 바뀌는 것은 하네스의 글(블록, 스킬, 역할, 템플릿)과 그것을 쓰는 명령이다.
- 차단 장치를 더하지 않는다(0.3 원칙). 흐름을 느슨하게 하는 대신 1차 감사가 머지 앞에 선다.
- intent 승인, spec의 진행/수정, 머지 지시, stable 지시는 그대로 명시적이다.
- 감사자는 읽기 전용·오프라인이다(0.3.1).
- 기존 설치는 `update`로 새 블록과 스킬을 받는다. 프로젝트 절(사용자가 쓴 AGENTS.md 본문)을 reins가 고치지 않는다.

## 열린 질문
1. **2차 감사의 시점.** "머지 및 배포 → 2차 감사"에서 배포를 rc로 볼지 stable로 볼지. PM 안: stable 배포 뒤, 회고 직전에 한 번(그 버전의 머지·rc·stable 과정을 한꺼번에 봄). rc마다 받는 안도 있다.
2. **기존 설치의 AGENTS.md.** `update`로 0.3.2를 받은 저장소에 "AGENTS.md를 가이드에 맞게 정리하라"는 표시를 남겨 다음 첫 대화에서 PM이 사용자와 정리하게 할까. PM 안: 남긴다(지금의 재구성 표시와 같은 방식, 한 번). 남기지 않고 새 설치·이전에만 적용하는 안도 있다.
3. **수용된 지적의 기준 횟수.** 사용자는 "서너번 이상"이라고 했다. PM 안: 세 번(회고가 세어 제안, 승격은 사용자가 받아들일 때).

| # | 정한 것 | 대안 | 이유 |

## 하지 않을 것

- 훅·CI에서 흐름을 막는 장치, 감사 결과를 세는 CLI.
- intent·spec 승인의 자동 수락, 머지·stable의 자동 실행.
- reins가 프로젝트의 AGENTS.md 본문을 자동으로 고치거나 옮기는 것(가리는 일은 PM이 사용자와 한다).
