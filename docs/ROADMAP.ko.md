# 로드맵

English edition: [ROADMAP.md](ROADMAP.md). 두 판이 다르면 한글 문서가 우선합니다.

버전 하나는 intent 묶음입니다. rc.1은 그 버전에서 계획한 것이 모두 끝났다는 뜻이고, 이후 rc는 안정화만 합니다. rc는 사람이 검증하며, stable 릴리스는 메인테이너가 명시적으로 지시할 때만 냅니다.

### 0.1.3 내용

- **단계 스킬.** 루프를 워크플로 단계마다 하나씩 열 개 스킬로 나눕니다. `reins-loop`는 이 스킬들을 순서대로 부르는 지휘자로 남습니다.
- **릴리스 흐름.** 배포 요약과 버전 동기화를 바로잡고, deploy 역할의 rc 흐름을 스킬로 적습니다.
- **회고와 knowledge.** 반복되는 사유를 세어 제안, 승인, 커밋을 거쳐 knowledge로 올리고, 찾는 데는 `reins recall`을 씁니다.
- **루프 수정.** ticket과 버스 요청을 손으로 쓰지 않고 `reins new`로 만들고, `--respond`가 verify 응답을 쓰며, `status`가 이미 릴리스된 intent의 마감을 다시 요구하지 않게 합니다.

### 0.1.5 내용

- **강제와 권고 구분.** README는 통제를 약속하지만, 역할 권한과 작업 범위, 예산은 아직 에이전트의 협조에 기대고 있습니다. 규칙마다 어떻게 지켜지는지를 한 줄로 적습니다. 스크립트나 훅이 막는 것, 전이 지점에서 검사하는 것, 역할과 스킬에 적혀만 있는 것으로 나눕니다. 이 표를 README 양판과 설계서에 넣고, 권고에 머문 규칙은 0.2의 입력으로 삼습니다. 모델 할당은 두 층으로 나눕니다. 커밋되는 `bindings.yaml`은 팀 기본값이고, gitignore되는 `.loctx/bindings.local.yaml`에 사용자별 덮어쓰기와 감지된 벤더를 둡니다. 역할이 실제로 쓸 모델은 스킬 지침으로 에이전트에게 맡기지 않고 CLI가 정합니다.
- **rc마다 문서 갱신.** rc도 결국 기본 브랜치로 merge되므로 문서도 그 시점에 맞아야 합니다. 로드맵 상태, CHANGELOG 절, README 상태 줄을 코드와 같은 릴리스 PR에서 고치고, 이전 상태가 남아 있으면 T5가 경고합니다.
- **여러 플랫폼 CI.** 패키지는 Node 20 이상을 선언하지만 CI는 Ubuntu와 Node 24만 봅니다. Node 20, 22, 24와 Windows, macOS에서도 `pnpm check`를 돌리고, 거기서 실패하는 것은 같은 버전에서 고칩니다.

## 0.2 — 0.2.0에서 닫음

| 버전 | 상태 | 내용 |
|---|---|---|
| 0.2.0 | 배포됨 | `reins config` TUI(모델과 역할, 나 또는 팀 범위, 역할 켜고 끄기), install과 update 화면 |
| 0.2.1~0.2.8 | 취소 | 0.3으로 대체(관리자, 2026-11-07) |

0.2 계획은 "에이전트가 하네스를 따르지 않는다"는 문제를 reins를 작업 안에 넣는 방식으로 풀려고 했습니다. 0.1.0부터 스킬과 git 훅이 `npx @bluenyang/reins`를 불렀고, 릴리스되지 않은 `feat/loop-enforcement` 브랜치는 프롬프트와 도구 호출마다 도는 런타임 훅, CLI가 소유하는 작업 단위·승인·감사까지 더했습니다. 그러면 적용 저장소가 일하는 동안 reins 패키지에 기댑니다. 캐시가 없는 오프라인 환경에서는 멈추고, 패키지가 오염되면 적용한 저장소가 모두 노출됩니다. 휘발성 파일도 일부만 지워졌을 뿐 수명 관리가 없었습니다. `feat/loop-enforcement`(intent 015~018)는 merge하지 않습니다.

## 0.3 — reins는 하네스 관리만 한다

상태: **0.3.0 배포됨**(2026-11-10, rc.4 커밋 그대로 stable). rc.3은 intent 020(개인 위임 표, 의미 있는 작업 단위 커밋, 감사용 PR·CI 기록)을 담았습니다. rc.4는 안정화 019 ST-8입니다. git 저장소 밖에서 실행하면 스택 트레이스 대신 무엇을 하라는 한 줄을 냅니다. rc.3을 확인하다 발견했고, 이 줄은 rc.4 감사의 지적에 따라 나중에 보완했습니다.

- **reins의 명령은 `install`, `migrate`, `update`, `config` 넷뿐입니다.** 프로젝트가 일하는 동안 어떤 훅도, 스킬도, 에이전트도 reins를 부르지 않습니다. 설치된 하네스는 reins와 네트워크 없이 동작합니다. 작업 중 쓰던 명령(`check`, `gate`, `new`, `status` 등)은 없앱니다.
- **검사는 프로젝트가 소유합니다.** 단계 검사는 lefthook·husky 같은 훅 도구나 프로젝트 안의 스크립트가 돌리고, reins는 설치할 때 제안하거나 설정합니다.
- **단일 에이전트가 기본입니다.** 멀티는 역할군(PM, PL, Planner, Implementer, Executor, Advisor, Auditor)에 모델을 할당해 켭니다. 할당하지 않은 역할군의 일은 PM이 합니다. 단일 모드에서도 PM은 조사·리뷰·감사 같은 읽기 위주의 일과 급한 병렬 작업에 같은 모델의 서브에이전트를 쓸 수 있습니다. 근거는 Anthropic의 [Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)(2026-10-22)입니다.
- **흐름과 단계 스킬.** `ROADMAP.local.md` → `ROADMAP.md` → intent(방향과 계획) → spec → 구현 → 테스트 → 머지 → 감사 → 릴리스 → 회고 → 정리. 스킬은 `onboard`, `roadmap`, `intent`, `spec`, `implement`, `review`, `test`, `merge`, `audit`, `release`, `retro`이고, 단일과 멀티가 같은 스킬을 씁니다. 순서는 AGENTS.md가 갖습니다.
- **버전마다 감사합니다.** 머지 뒤, rc 전에 단계를 지켰는지 감사하고 결과를 `.agents/audit/`에 커밋합니다. 사용자가 끄지 않는 한 필수입니다. 승인은 PM이 사용자의 말을 인용해 기록합니다.
- **설치 뒤 첫 대화는 온보딩입니다.** PM이 프로젝트를 파악하고 사용자에게 물어 AGENTS.md의 프로젝트 절(목표, 명령, 규칙, 금지선, 문서 언어)을 씁니다.
- **파일은 만들 때 수명을 정합니다.** 작업 중 기록은 회고 뒤에 지우고, history는 버전마다 한 장만 남깁니다.
- **기존 설치는 `update`로 옮깁니다.** 스킬과 훅의 reins 호출을 걷어내고, 쌓인 `.loctx` 파일은 확인을 받고 지웁니다.

### 0.3.1 — 배포됨

상태: **0.3.1 배포됨**(2026-11-11, rc.2 커밋 그대로 stable; intent 021). rc.2는 rc.1 배포본 확인에서 나온 안정화입니다. `update`가 훅 블록을 바꿀 때 그 블록에 있던 내용과, 합치지 못한 설정 파일·훅 제안을 출력에 보여 줍니다. 0.3 회고에서 나온 보완입니다(관리자, 2026-11-10).

- **회고가 knowledge 후보를 냅니다.** `retro` 스킬이 history와 감사에서 반복된 결정·실패를 찾아 knowledge 후보로 제안합니다. 설계 §8에는 있었지만 스킬에 빠져 있어서, 0.2.0은 회고 없이 지나갔고 0.3 동안 승격이 없었습니다.
- **`.claude/settings.json`은 합칩니다.** `update`가 이 파일을 통째로 비교하지 않고, 사용자가 넣은 항목(allow 등)을 남긴 채 reins의 항목만 고칩니다. 지금은 허가 한 줄만 더해도 "손으로 고침"으로 건너뛰고, `--force`면 사용자 허가가 사라집니다.
- **감사자는 읽기 전용입니다.** 감사자 실행 줄을 읽기 전용으로 바꾸고, 감사 기록은 PM이 씁니다.
- **커밋마다 검사 출력을 남깁니다.** 훅이 돌린 프로젝트 검사의 출력이 남아, 감사가 커밋별 통과를 확인할 수 있습니다. 프로젝트 안의 스크립트 하나가 검사를 돌리고 출력을 남기며, 어느 훅 도구든 그 스크립트를 부르는 한 줄을 씁니다. 로그가 없는 커밋(rebase로 다시 만든 것 등)은 감사 전에 PM이 그 커밋에서 검사를 돌려 채웁니다. 훅은 프로젝트 검사만 돌리고 reins를 부르지 않습니다.
- **실행 줄의 명령 이름.** 설정에 벤더의 CLI가 적혀 있지 않으면 위임 표가 벤더 이름(`openai exec …`) 대신 그 벤더의 기본 명령(`codex exec …`)을 씁니다(0.3.1 리뷰에서 발견).
- **테스트 수정.** e2e 테스트가 node 옆에 전역 설치된 reins 때문에 실패하지 않게 합니다(0.3.1 준비 중 발견). 감사 뒤 리뷰에서 나온 보완: 시스템 경로(`/usr/bin`)에 전역 reins가 있어도 실패하지 않게 합니다.
- **영문 설계서 두 문장.** 감사 뒤 양판 대조에서 국문과 다르게 적힌 곳을 맞춥니다.
- **검사 다시 찾기.** `config gates --refresh`가 설치 때와 같은 탐색을 다시 돌려 `gates.yaml`과의 차이(새로 찾은 검사, 명령이 달라진 검사, 출처가 사라진 검사)를 보여 주고, 고른 것만 반영합니다. `config` 화면에서도 검사 설정을 보고 다시 찾을 수 있습니다.
- **대체 모델(fallback).** 역할에 대체 모델을 적어 둘 수 있습니다. `config`가 위임 표의 그 역할에 대체 실행 줄을 미리 적고, 호출이 안 되면 PM이 그 줄을 따릅니다. 작업 중에 reins가 해석하는 것은 없습니다.
- **알려진 모델 목록 갱신.** `config`가 제안하는 모델 목록을 현재 모델에 맞춥니다. `claude-fable-5-2`는 고를 수 있는 모델로 두되, 이 환경에서 동작을 확인한 목록에는 넣지 않습니다(감사 뒤 결정).
- **`AGENTS.previous.md` 머리 경고.** 0.2.0 이하 설치를 `update`로 옮길 때 만드는 사본 머리에, 0.2.0 이하의 지시 사본이며 거기 적힌 reins 명령은 0.3에 없으니 실행하지 말라고 적습니다.

### 0.3.2 — 배포됨

상태: **0.3.2 배포됨** (2026-11-15, rc.1 커밋에서 stable; intent 022).

0.3.1을 만들며 드러난 흐름의 빈 곳을 메웁니다(관리자, 2026-11-11; 배경은 [설계 대화](conversation/2026-11-11_flow-audit-agents-md.md)).

- **승인 뒤는 하나의 흐름.** intent와 spec을 승인하면 구현, 리뷰, 테스트, PR, CI까지 묻지 않고 이어 갑니다. 머지와 stable 릴리스는 계속 지시를 받습니다.
- **작업 중 spec 조정.** 작업 단위를 더하거나 빼거나 범위를 바꾸는 것은 멈추고 승인받습니다. 같은 단위 안의 방법 변경과 리뷰·감사에서 나온 작은 보완은 진행한 뒤 보고합니다.
- **감사 두 번.** CI가 통과하면 머지 전에 1차 감사가 위험을 보고, 머지와 배포 뒤 2차 감사가 절차만 봅니다. 2차의 결과는 회고로 넘깁니다. 기록이나 문서를 고쳤다고 다시 감사하지 않습니다.
- **수용된 지적.** 여러 번 반복되고 매번 수용된 감사 지적은 knowledge에 적어 두고, 감사는 그것을 위반 대신 알려진 수용으로 표시합니다.
- **AGENTS.md 가이드와 온보딩.** AGENTS.md에는 프로젝트의 목표, 구조, 공통 규칙과 중요한 지시만 둡니다. 설치·이전 뒤 첫 대화에서 기존 내용을 가려 진행 상황은 로드맵으로, 결정은 knowledge로, 개인 메모는 `.loctx`로 보냅니다.
- **루프의 끝.** 한 루프는 사용자가 지시한 작업 단위(보통 한 버전)와 그 회고까지입니다. 회고가 루프를 끝냅니다. PM은 보고하고 멈추며, 다음 intent는 사용자가 시작하라고 할 때 씁니다. 사용자가 끝을 다르게 말했으면("0.4까지 진행", "멈추지 않고 진행") 그 말을 따릅니다. 루프 안에서 사용자를 기다리는 곳(배포 승인, 머지·stable 지시)에서는 보고하고 기다리며, 그 시간을 다음 단위의 일로 채우지 않습니다. 버전을 고른 것은 시작 지시가 아니며, 다음 아이디어는 언제든 로드맵에 적습니다(0.3.1 회고: 이 버전 intent의 첫 초안이 0.3.1-rc.1 배포 직후에 쓰였습니다).
- **PM은 지금 대화하는 모델.** 하네스가 PM의 모델을 정하지 않습니다. 위임 블록은 "you are the PM"이라고만 적고, 모델을 배정하지 않은 역할과 감사는 그 모델이 합니다. `config`는 다른 모델이 필요한 역할에만 모델을 배정합니다.
- **여기서 겪은 하네스 문제는 하네스에서 고칩니다.** 기능과 에이전트 제어에 관한 것은 이 저장소의 관례에서 스킬로 옮깁니다. 머지 지시가 어느 PR을 말하는지는 PM이 판단하고(제안한 것, 방금 말한 PR) 가릴 수 없으면 묻습니다. 머지한 브랜치는 머지 단계에서 지웁니다. 머지가 SHA를 바꾸면 기록은 기본 브랜치의 SHA를 적습니다. 프로젝트마다 다른 것(문서 언어, 커밋 메시지 형식)은 올리지 않습니다.
- **0.3.1 회고의 작은 보완 둘.** `review` 스킬은 테스트만 고친 작업 단위도 리뷰하거나, 하지 않았다고 기록하게 합니다. `update` 보고는 다시 쓴 기존 생성 파일을 새 파일로 표시하지 않습니다.

## 0.4 — 적용

## 1.0 — 일정 없음

reins는 0.x에서 기능을 더해 가다가 메인테이너가 체계가 잡혔다고 판단할 때 1.0이 됩니다. 안정화만으로는 1.0이 되지 않습니다. 그때까지 파일 형식(스키마 `@1`)이 마이너 버전에서 바뀔 수 있고, 바뀌면 `update`나 `migrate`가 기존 설치를 옮깁니다.
