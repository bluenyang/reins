# 로드맵

English edition: [ROADMAP.md](ROADMAP.md). 두 판이 다르면 한글 문서가 우선합니다.

버전 하나는 intent 묶음입니다. rc.1은 그 버전에서 계획한 것이 모두 끝났다는 뜻이고, 이후 rc는 안정화만 합니다. rc는 사람이 검증하며, stable 릴리스는 메인테이너가 명시적으로 지시할 때만 냅니다.

### 0.1.3 내용

- **단계 스킬.** 루프를 워크플로 단계마다 하나씩 열 개 스킬로 나눕니다. `reins-loop`는 이 스킬들을 순서대로 부르는 지휘자로 남습니다.
- **릴리스 흐름.** 배포 요약과 버전 동기화를 바로잡고, deploy 역할의 rc 흐름을 스킬로 적습니다.
- **회고와 knowledge.** 반복되는 사유를 세어 제안, 승인, 커밋을 거쳐 knowledge로 올리고, 찾는 데는 `reins recall`을 씁니다.
- **루프 수정.** ticket과 버스 요청을 손으로 쓰지 않고 `reins new`로 만들고, `--respond`가 verify 응답을 쓰며, `status`가 이미 릴리스된 intent의 마감을 다시 요구하지 않게 합니다.

### 0.1.5 내용

- **강제와 권고 구분.** README는 통제를 약속하지만, 역할 권한과 작업 범위, 예산은 아직 에이전트의 협조에 기대고 있습니다. 규칙마다 어떻게 지켜지는지를 한 줄로 적습니다. 스크립트나 훅이 막는 것, 전이 지점에서 검사하는 것, 역할과 스킬에 적혀만 있는 것으로 나눕니다. 이 표를 README 양판과 설계서에 넣고, 권고에 머문 규칙은 0.2의 입력으로 삼습니다. 모델 할당은 두 층으로 나눕니다. 커밋되는 `bindings.yaml`은 팀 기본값이고, gitignore되는 `.loctx/bindings.local.yaml`에 사용자별 덮어쓰기와 감지된 벤더를 둡니다. 역할이 실제로 쓸 모델은 스킬 지침으로 에이전트에게 맡기지 않고 CLI가 정합니다.
- **rc마다 문서 갱신.** rc도 결국 기본 브랜치로 merge되므로 문서도 그 시점에 맞아야 합니다. 로드맵 상태, CHANGELOG 절, README 상태 줄을 코드와 같은 릴리스 PR에서 고치고, 이전 상태가 남아 있으면 T5가 경고합니다.
- **여러 플랫폼 CI.** 패키지는 Node 20 이상을 선언하지만 CI는 Ubuntu와 Node 24만 봅니다. Node 20, 22, 24와 Windows, macOS에서도 `pnpm check`를 돌리고, 거기서 실패하는 것은 같은 버전에서 고칩니다.

## 0.2 — 루프 재구성, graph에서 loop·harness 깎기, 이기종 에이전트

입력: 0.1에서 쌓은 metrics와, reins를 적용한 저장소에서 난 사고입니다. 그 저장소에서 에이전트가 하네스를 통째로 건너뛰었습니다. intent·ticket·승인·리뷰·history가 하나도 없었고 모델 바인딩도 우회했는데, pre-commit은 모든 커밋을 통과시켰습니다. 원인은 개별 규칙의 빈틈이 아니라 구조였습니다. 루프에 들어오는 것, 전이 검사, 승인 기록, 리뷰, 기록을 모두 통제받는 에이전트가 스스로 불러야 했습니다.

순서는 관리자가 정했습니다(2026-10-28 개정). **루프 재구성이 먼저**이고, 그다음은 적용 준비, 강제, 예산, 벤더 순서입니다. 깎기는 수치가 쌓인 뒤 마지막에 합니다. 0.2.1~0.2.3이 끝나기 전에는 0.3 적용을 하지 않습니다.

0.2.1~0.2.3은 설계서(`docs/design.md`, 한글판)를 먼저 고치고 코드를 짭니다. 원칙 1(이식성과 검증 독립성 분리), 원칙 2(상태 기반 규칙), 원칙 3(실행·전이·증거 수집은 스크립트 소유), §4 승인 형식, §6 생성물, §8 기록 입력이 바뀝니다. "CLI는 모델을 부르지 않는다"는 그대로 둡니다.

### 0.2.1 내용 — 루프 강제

- **작업 단위를 reins가 소유.** 활성 작업 단위와 그 전이를 CLI가 기록하고, 훅·T2·T4·T5·CI가 같은 상태를 읽습니다. 저장소를 쓰지 않는 읽기·분석에는 단위가 필요 없습니다.
- **작업 단위 없는 커밋은 STOP.** T2가 활성 단위, 유효한 승인, 변경 범위를 확인합니다. 리뷰 완료는 커밋마다 요구하지 않고 종료 시점에 요구합니다.
- **에이전트 런타임 훅.** 설계 §6에 있었지만 생성되지 않던 훅을 생성합니다. 세션 시작과 프롬프트에서는 상태를 주입합니다. 도구 호출 전에는 작업 단위 없는 쓰기, `reins-*`가 아닌 서브에이전트와 바인딩과 다른 모델, 에이전트가 직접 하는 승인 쓰기를 막습니다. 리뷰 없이 끝나는 단위도 막습니다. 이번 버전은 Claude Code만이고, 다른 벤더는 0.2.7에서 합니다.
- **승인 재설계.** 승인은 사람이 권한 확인 창에서 허락해야 실행되는 `reins approve`로만 합니다. 증빙은 승인 대상의 개정·범위·주체·시각에 묶고, 지난 트레일러는 다시 쓰지 못합니다. 위임에 따른 자동 수락(spec 요약)은 `Accepted-by:`로 따로 둡니다.
- **기록은 CLI가.** 단위의 시작·커밋·거부·리뷰·종료를 CLI와 훅이 append-only로 남기고, 단위 없이 한 커밋은 `off-loop`로 기록해 retro가 셉니다. 에이전트는 이 기록을 보고 history 서술만 씁니다. 단위를 닫을 때 history 요약이 있는지 확인하고 그 단위의 bus 파일을 CLI가 지웁니다. 지금은 에이전트가 지우게 되어 있어서 닫힌 ticket의 bus가 쌓였습니다.
- **easy 등급.** 작은 수정은 명령 한 줄로 단위를 열고, 요청 자체를 허가로 봅니다. 사후 보고와 독립 리뷰가 있고 사용자는 거부권을 가집니다. 강제와 같은 버전에 나가야 합니다. 무거운 경로만 있는 채로 STOP을 걸면 우회하려는 압력이 커집니다.

### 0.2.2 내용 — 작업 등급과 문서 루프

- **easy / common / complex.** 에이전트는 등급을 제안만 합니다. CLI가 객관 신호(바뀐 파일과 경로, 스키마·하네스·공개 API 변경, diff 크기)로 T2와 종료 시점에 확인하고, 맞지 않으면 등급을 올립니다. 사용자는 언제든 바꿀 수 있습니다. complex는 지금의 intent → spec → plan → ticket이고, common은 그보다 가볍습니다.
- **묶음 승인.** 승인은 intent·plan 단위로 한 번 받고, 병렬 ticket은 그 승인을 이어받습니다.
- **문서 루프.** 문서 검증은 근거를 찾는 일입니다. 범위와 독자 → 주장 추출 → 주장마다 근거(code path:line, 테스트, 커밋, knowledge) 연결 → 다른 모델이 근거를 다시 찾아 확인 → 작업 중 발견한 결함은 원장과 ticket으로 기록 → 윤문은 마지막에 합니다.
- **독립 리뷰가 종료 조건.** 리뷰어는 설정이 고르고, reins가 실행 사실(벤더·모델·대상 커밋)을 기록합니다. 작성자와 같은 모델의 리뷰로는 단위가 닫히지 않습니다. 다른 벤더가 없으면 다른 모델로 하고 "독립성 저하"로 기록합니다.
- **merge·릴리스 재검증.** T4·T5와 PR CI가 승인, 리뷰, 최종 diff 일치를 다시 봅니다. 강제와 권고 표에는 적용 벤더와 우회 경로를 함께 적습니다.

### 0.2.3 내용 — 논의와 총괄

- **discussion 단계.** 요구는 처음부터 나오지 않고, 말로 풀고 논의하면서 드러납니다. roadmap 앞에 논의 단계를 둡니다. 아이디어와 선택지, 근거, 수용·기각·보류와 그 이유를 기록하고, 기각된 것은 C8의 근거가 됩니다. 비슷한 주제가 다시 나오면 그 기록을 알립니다.
- **총괄은 PM과 PL이 함께.** 간단한 일은 PM이 혼자 합니다. 복잡한 일은 PM이 여러 PL의 의견을 참고하고, 각 PL은 다른 에이전트의 탐색·조사 결과를 받아 의견을 냅니다. 에이전트도 사용자의 지시보다 먼저 다른 방향, 방법론, 가능성을 제안할 수 있습니다. 최종 수용과 기각은 사용자가 합니다.
- **PL 사이 교차검증.** 복잡한 일에서는 PL들이 서로의 결과를 보지 않고 따로 판단합니다. 사용자에게는 견해와 갈린 지점을 함께 보여 줍니다. 채점은 이견을 드러내는 데만 쓰고 자동 결정에는 쓰지 않습니다.

### 0.2.4 내용 — 적용 준비

- **stable도 merge 전에 릴리스 문서 갱신.** 문서만 바꾸는 stable PR(intent `released`, 날짜가 붙은 CHANGELOG `[V]`, 로드맵 행, README 상태 줄)을 먼저 merge하고 stable을 배포합니다. publish 워크플로는 HEAD가 마지막 rc 태그와 같아야 한다는 조건 대신, 그 태그 이후 바뀐 것이 `release.docs` 파일과 해당 버전 intent의 상태뿐이면 stable을 받습니다.
- **Python 게이트.** 게이트 탐색이 `pytest`, `pyproject.toml`, `requirements.txt` 프로젝트를 찾습니다. 하위 디렉터리처럼 제안만 합니다.
- **버전별 migrate.** `migrate`가 열린 work를 intent 000 하나로 묶지 않고 버전마다 초안 intent로 나눕니다.
- **`.loctx` 보존 정책.** 경로마다 수명(단위 종료까지, 버전 stable까지, 영구)을 정책 파일에 적고, `reins prune`이 그에 따라 정리합니다. `--dry-run`은 목록만 보여 주고, 실제 삭제는 확인을 거칩니다. 게이트 로그는 해당 버전의 stable이 나간 뒤에 지웁니다. history, metrics, release 기록은 영구입니다. reins가 만들지 않은 경로(다른 스킬의 작업 폴더 등)는 지우지 않고 목록에만 올립니다.

### 0.2.5 내용 — 남은 강제

0.1.5에서 권고로 분류한 규칙([표](README.ko.md#강제와-권고), 원천 [`enforcement.yaml`](../harness/policy/enforcement.yaml)) 가운데 0.2.1~0.2.2에서 다루지 않은 것을 강제로 바꿉니다. `.env` 읽기 차단(예제 파일은 읽을 수 있음), C6, C10의 plan 비교, 그리고 꺼진 역할의 ticket을 T1이 거부하는 것입니다. 바뀐 규칙은 표에서도 함께 옮깁니다.

### 0.2.7 내용 — CLI는 여전히 모델을 부르지 않음

설계 불변식은 그대로 둡니다(관리자 결정, 2026-10-28). reins는 벤더마다 파일과 런타임 훅을 생성하고, 역할이 그 벤더에서 실행할 명령 줄을 정확히 보여 줍니다. 실행은 에이전트가 합니다. reins가 벤더 CLI를 직접 띄우지는 않습니다.

## 1.0 — 일정 없음

reins는 0.x에서 기능을 더해 가다가 메인테이너가 체계가 잡혔다고 판단할 때 1.0이 됩니다. 안정화만으로는 1.0이 되지 않습니다. 그때까지 파일 형식(스키마 `@1`)이 마이너 버전에서 바뀔 수 있고, 바뀌면 `update`나 `migrate`가 기존 설치를 옮깁니다.
