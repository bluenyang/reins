# 설계 대화

reins를 만들면서 메인테이너가 무엇을 고민했고, 그래서 각 버전이 왜 그런 모양으로 나왔는지를 시기별로 남깁니다. 코드와 [설계서](../design.ko.md)에는 정한 결과만 있고, 이 폴더에는 그 결과에 이르는 길이 있습니다. 메인테이너의 엔지니어링 기록이라 한글로만 씁니다.

어느 문서도 규칙이 아닙니다. 주제마다 "상태"에 그 생각이 어느 버전에 들어갔는지, 뒤에 바뀌었는지를 적었습니다.

| 시기 | 버전 | 문서 | 한 줄 |
|---|---|---|---|
| 2026-10-22~25 | 기획 | [왜 reins를 만들었나](2026-10-22_why-reins.md) | 단계마다 명령을 내리던 루프의 한계, 하네스를 설치·이전하는 도구라는 출발점 |
| 2026-10-26~27 | 0.1.0~0.1.5 | [검증기와 게이트로 통제하려 했던 0.1](2026-10-26_0.1-verifier-and-gates.md) | 검사는 멱등한 도구가 한다. 그 도구가 reins가 되면서 생긴 허점 |
| 2026-10-27~11-07 | 0.2.0, 취소된 0.2.1 | [더 강하게 막으려다 방향을 잃은 0.2](2026-10-27_0.2-enforcement-and-stop.md) | 설정 화면, 런타임 강제, 그리고 멈춘 이유 |
| 2026-11-07~10 | 0.3.0 | [reins는 하네스만 관리한다](2026-11-07_0.3-harness-only.md) | 작업 중에 reins를 부르지 않는다. 막지 않고 감사한다 |
| 2026-11-10~11 | 0.3.1 | [0.3.1을 만들며 다시 생각한 것](2026-11-11_flow-audit-agents-md.md) | 검사 기록, 설정 합치기, 대체 모델, 그리고 흐름의 빈 곳 |
| 2026-11-12~ | 0.3.2 | [루프가 어디서 끝나는가](2026-11-12_0.3.2-loop-and-audits.md) | 승인 뒤 하나의 흐름, 감사 두 번, 회고가 루프의 끝, PM은 대화하는 모델 |

기록이 남지 않은 구간(0.1.0과 0.1.1을 만든 2026-10-25 저녁~10-26 아침)은 메인테이너가 나중에 따로 설명한 것으로 채웠고, 그렇다고 본문에 밝혔습니다. 기록에 이유가 없어 정리하며 추정한 곳도 그렇게 표시했습니다.
