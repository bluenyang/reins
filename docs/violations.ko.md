# reins — 누가 어떤 위반을 잡나

> 한글 원본. 영어판은 [`violations.md`](violations.md) — 둘이 어긋나면 이 파일이 기준이다. [`design.ko.md`](design.ko.md) §3의 짝 문서.

0.2.0까지는 검증기(`reins check`)가 정해진 지점에서 돌며 위반을 그 자리에서 멈췄다. 이 표를 뒷받침하던 시나리오 묶음(V1~V25)은 git 이력(`v0.2.0` 태그)에 있다. 0.3에서는 프로젝트가 일하는 동안 아무것도 reins를 실행하지 않으므로(설계 §0), 물음은 "어느 단계가 막나"가 아니라 "누가 알아채나"다.

| 종류 | 잡는 쪽 | 언제 |
|---|---|---|
| 비밀 파일 읽기(`.env`, `secrets/**`, 키) | 에이전트 호스트, 생성된 거부 규칙(`.claude/settings.json`) | 읽기 전(Claude Code) |
| force push, `--no-verify` | 생성된 거부 규칙 | 명령 전(Claude Code) |
| 실패하는 검사 | 프로젝트의 훅과 CI(`gates.yaml` 명령) | 커밋, push, PR 때 |
| 흐름의 단계를 건너뜀(intent·승인·spec·리뷰·테스트·감사 없음) | 버전 **감사** | 머지 뒤, rc 전 |
| 사용자가 하지 않은 승인 | 감사(승인은 사용자 말을 인용하고 개정을 가리킴), 감사 보고를 읽는 사용자 | 머지 뒤 |
| 생성 파일·하네스 파일 손 수정(드리프트) | 감사(git 이력), `reins update`(덮어쓰기 전 확인) | 머지 뒤, update 때 |
| "통과하기 위한" 구현, spec 밖 변경, 지난 결정 뒤집기 | 리뷰(리뷰어 하나, 큰 결정은 Discussion)와 plan-reviewer | 리뷰 때 |
| 사용자가 원한 방향에서 벗어남 | 사용자, plan-reviewer, 회고 | 승인할 때마다, 릴리스 뒤 |

감사는 단계마다 지킴·위반·확인 불가(증거 경로 없음)·사용자 지시로 건너뜀을 판정한다. 위반은 보완하거나 사용자가 받아들이고, 어느 쪽이든 감사와 회고에서 비판한다. 감사를 통과해도 방향이나 코드 품질의 보증은 아니다.
