# audit

## 1. When
Twice in a version. The **first audit** comes after CI passes and before the merge. The **second audit** comes after the stable release (or when the user closes a version that has none), right before the retro. While `audit.required` in `.agents/harness/bindings.yaml` is true, both are mandatory — never skip one.

## 2. Procedure
Both audits run in a fresh context that gets only the records, never the working conversation (auditor if switched on; without one, a new run of your own model, or another one the user chooses). The audit runs without a network; a record it lacks is "cannot confirm" and is asked of the PM. The audit run is read-only: it returns the record as its answer, in the form of `.agents/harness/templates/audit.md`. The PM keeps that answer as it came under `.loctx/reports/<version>/` and writes it unchanged to `.agents/audit/<version>.md` — never rewording, shortening or dropping a verdict. An audit goes through the history, finds what went wrong and says what to put right; it does not check every commit against every sentence of the rules.

### First audit — before the merge
1. It audits the PR that carries the accepted spec's work units (units added with approval too), on its branch. A PR of records, documents or release documents only, and the PR of a small fix made as an adjustment after the first audit, go without one: say so and why in one line of the PR body. The second audit looks at those merged before it.
2. Before handing the audit over, the PM collects the PR and its CI checks as the repository host's CLI prints them, unedited (e.g. `gh pr view <n> --json number,headRefOid,body`, `gh pr checks <n>`), into files under `.loctx/reports/<version>/`, and passes their paths to the audit. Do not summarise or rewrite them. Then fill in the gate logs: for every commit of the branch, `.loctx/reports/gates/<tree>.log` (`<tree>` is `git rev-parse <commit>^{tree}`) should hold a run with `worktree: clean` and `exit: 0`. Hooks leave these logs as you commit, but a commit made again by a rebase, on another machine or past the hook has none. For each commit without one, with a clean work tree: `git checkout --detach <commit>`, prepare it as the project needs (install dependencies), run `sh .agents/harness/run-gates.sh audit`, and return to your branch. Do not fix a run that fails; pass it on as it is. If the project has no `run-gates.sh`, say so instead.
3. Read: AGENTS.md and the harness settings as they were, the intent, spec, `docs/ROADMAP.md`, `.loctx/ROADMAP.local.md`, `.agents/knowledge/`, git history, history, gate and test logs, the gate logs per commit (`.loctx/reports/gates/<tree>.log`), the PR and CI records the PM collected (`.loctx/reports/<version>/`).
4. Look for **risk**, step by step: local roadmap → roadmap → intent → approval → spec → approval → implementation and commits → review → test → PR and CI. Kept, violated, cannot confirm (no evidence path), or skipped on the user's instruction (recorded in `waivers:`). Judge against the rules in force at the time. What counts as risk: an approval that is missing or was not given by the user; scope beyond the intent and spec; a red line; a work unit that was not reviewed; a check that failed or cannot be confirmed; a generated or harness file changed by hand. Commits: each commit is a meaningful unit — a point you can revert or reset to without taking other working work or features with it; several commits for one work unit (implementation, review fixes) are fine, and small units that may be reverted together may share one. A commit that mixes unrelated work, so one part cannot be reverted alone, is a violation. Gates: for each commit, the log of its tree holds a run with `worktree: clean` and `exit: 0` — say whether it was left at commit time (`stage: pre-commit`, `pre-push`) or filled in before the audit (`stage: audit`); no such run is "cannot confirm", and a clean run whose last `exit:` is not 0 is a violation. A work unit added, dropped or rescoped without approval is a violation; an adjustment recorded in the spec is kept; an adjustment made without a record is a violation whose remedy is the record. A generated or harness file changed by a commit that is not an `update`/`config` commit is a violation. In `.claude/settings.json` only reins' deny rules count (listed under `owned:` in `.agents/harness/generated.yaml`); the user's own entries there are not drift.
5. Criticise each violation precisely and give a remedy (pl or advisor opinions by severity). The PM writes the answer under `## 1차 감사` and commits the record on the PR branch, so that it is merged with the work. Push it: that commit moves the PR's head, so wait for CI again.
6. The PM reports to the user — this is the one report of the flow (`merge`): fix a violation before the merge, or the user accepts it. Write the user's decision under `### 사용자 처리`, commit and push; a fix goes the same way, and the merge waits until CI is green on the last of these commits. A fix made after the audit is not audited again; only a high-risk violation whose fix is a large change is, and the PM writes there which it was and why.

### Second audit — after the release
1. Before handing the audit over, the PM collects for every PR merged in the version — its number, who merged it and when, the merge commit and head SHA, each CI check and its result — as the host's CLI prints them, unedited (e.g. `gh pr view <n> --json number,mergedBy,mergedAt,mergeCommit,headRefOid,body`, `gh pr checks <n>`); the user's words for each merge; the records of the releases (the workflow runs, the tags); the table of branch SHAs and default-branch SHAs, when a merge rewrote the commits; and the gate logs of the commits made after the first audit's head, filled in as above.
2. It looks at **procedure only**, from the first audit's head to the version's last commit: whether each merge had the user's instruction and how it was merged; the CI and release records; the release documents; and whether the records are complete — the user's decisions on the first audit, waivers, the spec's adjustment record, the reason line of each PR that went without a first audit.
3. It does not tell anyone to fix anything: it lists what is handed to the retro. The PM writes the answer under `## 2차 감사` and, beneath it, the SHA table under `### SHA 대응`. There is no user decision here: the retro reads it, and what the user decides there goes under `### 회고에서의 처리`. The record is committed with the retro's commits, in one PR. That closing PR — this record, the retro's changes — is audited by neither audit.

## 3. Delegation
Check `.loctx/delegation.local.md` if it exists, otherwise the delegation table in AGENTS.md. If the role group named here has a model, hand it the work with the list of files and decisions it needs and wait for its report; otherwise do it yourself. Read-heavy work (research, large log summaries, review) or urgent parallel work on independent units may go to subagents of your own model. A role never calls another model; it returns to you. The audit never runs inside the working conversation.

## 4. Files and lifetime
- `.agents/audit/<version>.md` — one file per version with both audits; committed, kept.
- `.loctx/reports/<version>/` PR and CI records, and the audit run's answer as it came — deleted after the retro, once summarised in the audit record.
- `.loctx/reports/gates/<tree>.log` — written by the hooks and by the PM before each audit; deleted in the retro.

## 5. Next
After the first audit: `merge` (the merge itself). After the second: `retro`.

## 6. Stop and ask
- A passing audit does not vouch for direction or code quality; say so in the report.
